# Workflow v2

Type: map

## Destination

A one-page spec for a two-speed way of building: a fast lane that takes an idea through a prototype to an MVP, a careful lane for products that graduate, and the rule that moves one to the other. It also covers a brainstorm session every two to four weeks that picks the next product, and one repo that is safe to publish as it stands: no scrub step, one install that works the same for Abdul and for anyone else, and a README that tells the version 1 to version 2 story. The same install brings the toolbox to the GitHub Copilot app Abdul uses at work. A regular audit keeps the workflow from growing back. A later session builds the spec.

Reached on 2 November 2026: [the spec](spec.md).

## Notes

- Domain: Abdul's own Claude Code setup. The skills live in this repo, the hooks in `~/.claude/hooks/`. At work he uses the GitHub Copilot app, on a Windows machine where he cannot install .exe files.
- Why now: Orderflow, the order app, took 728 issue files and 2,528 commits between 9 September and 24 October 2026. It is finished and runs the orders of a real business, but one product in six weeks is too slow. Abdul wants a real product every two to four weeks, with small MVPs between.
- Abdul does not read issue files or PRs. He reads the idea, then the product. Anything the new workflow asks him to read must fit on one page.
- Abdul is an engineer first. The public repo must show engineering judgement and a handful of good products, never a pile of MVPs. Its first reader is a future employer who arrives from LinkedIn and judges on the first screen.
- Plan, don't do. Tickets end in decisions; building starts after the map.
- The simpler road wins. A ticket that recommends the heavier option says what the lighter one would cost.
- Grilling tickets use /grilling and /domain-modeling. Ticket text follows /writingrules. Replies to Abdul follow ASD-STE100.
- parallel-hunt survives in some form. Abdul says it still finds real bugs.
- No version 2 session or agent goes past 400k tokens of context, and the aim is 300k; Abdul finds agents make mistakes beyond that. One setting compacts every session at 400k now, and the window drops to 300k once sessions start smaller than today's 100k.

## Decisions so far

- [How Claude Code can run a scheduled session](issues/05-scheduling-options.md): a cloud routine on a monthly or twice-monthly cron, continued by Abdul from claude.ai.
- [How fast solo builders ship with Claude Code today](issues/02-how-fast-builders-ship.md): a one-page spec, small features each with a check the agent runs, one fresh review; keep customer data, money and auth out of the fast lane.
- [What each skill and hook does today](issues/04-inventory-skills-and-hooks.md): 35 skills and 33 hooks; 17 hooks exist only to guard run-issues, and the 15 skills that suit a fast lane carry nothing private.
- [What in this repo is private](issues/06-private-material-in-the-repo.md): no secrets, but project names, home paths and run history in hundreds of files; the scrub ran every 2.2 days and still leaks.
- [What recent Claude Code features and Anthropic posts can replace](issues/13-recent-claude-code-features.md): built-in workflows, /code-review, /goal with auto mode and plugin install can replace most of run-issues, its hooks and the scrub step.
- [What the fast lane does, from brief to done](issues/01-fast-lane-from-brief-to-done.md): a one-page brief, an approved prototype that becomes the first commit, one auto-mode build session, done when live and matching the prototype; any feature allowed, nothing real.
- [What moves an MVP to the careful lane](issues/03-graduation-test.md): Abdul graduates an MVP when he can name a person who will put real data in within a week; the brainstorm session gives each MVP graduate, keep (once) or stop; the pre-launch gate runs first; one way, no skipping the fast lane.
- [How the brainstorm session works](issues/07-brainstorm-session.md): a cloud routine on the 1st and 15th prepares one page; Abdul reviews open MVPs first, then picks at most one idea, which leaves with a draft brief; idea log and MVP list live in a private `roufmlp/ideas` repo.
- [What the careful lane keeps](issues/08-what-the-careful-lane-keeps.md): the fast lane's loop plus checks, one change note per session; the chain, the queue and daily-brief retire; a smaller parallel-hunt on command; 23 skills in one toolbox for both lanes; 6 hooks stay.
- [One repo that is safe to publish](issues/09-one-public-safe-repo.md): version 2 lands in `agent-skills`, with version 1 tagged and kept restorable; a `commit-msg` hook refuses client names and home paths, and an agent changes it only with Abdul's approval; private material lives in `~/.claude/`, the ideas repo and each product's repo; the spec and this map go public.
- [How someone installs it](issues/10-install-path.md): a `workflow` plugin, one command, no questions; Abdul's working copy is the plugin itself; only a push to the `release` branch reaches friends and the Copilot app at his work, which gets skills and agents but no hooks; a check on every push and a refusal eval each week.
- [How the README tells the version story](issues/11-version-story.md): the README opens on the cut, for a future employer from LinkedIn: the pipeline that built Orderflow, measured and mostly cut, then two lanes and a product every two to four weeks; the plugin depends on Matt Pocock's plugin for his 18 skills instead of copying them.
- [What version 1 cost, and where its time went](issues/17-version-1-cost.md): 69 minutes of run time per shipped issue across version 1, 68.7 for Orderflow; implementing took 54.5% of the agent hours and the two gates 40%; the records cover only the build loop, and 53% of Orderflow's commits landed outside it.
- [What happens to Orderflow](issues/12-orderflow-fate.md): version 1 holds until Abdul says request-kinds is finished; at the switch a sweep turns the 28 risk-class items still true into draft change notes, Orderflow gets a brief, `.scratch/` stays behind at a `v1` tag, and the evening check only sorts.
- [How a regular audit keeps the workflow small](issues/14-workflow-audit.md): a weekly local script summarises sessions; on the 1st the brainstorm page gets a ten-row table (cost, tokens, decisions, interruptions, bugs, drift and growth among them); a budget in the push check refuses growth unless Abdul raises it; the audit proposes and never removes.
- [How the careful lane keeps every slice aligned to the core design](issues/15-careful-lane-alignment.md): a one-page core design written at graduation (screens, patterns, modules); a screenshot test, a check per pattern and ESLint import rules refuse drift; a note check refuses a core-design change or a big change without Abdul's approval and, for screens, a prototype.
- [How long Orderflow's test suite takes, and where it flakes](issues/20-orderflow-test-suite.md): 9.0 minutes a run by late October, double the late-September figure, 2.2 to 2.8 runs per issue; flakes hit at most one run in four; `vitest related` reaches a large share of the suite for a typical change.
- [Which steering files each lane loads, and the new CLAUDE.md](issues/16-steering-files-per-lane.md): each set of rules is the body of its own skill and ships in the plugin, with no other copy; the lane lives in each product's `CLAUDE.md`; the global file keeps about 80 lines; one private pending file holds actions and the decisions that unattended sessions could not take alone.
- [What happens to procurement and the other chain work](issues/18-procurement-fate.md): procurement holds real data, so it is a product; it joins the careful lane at the switch, parked until the brainstorm session picks its revamp; its 157 open issue files stay at the `v1` tag, the app goes offline now, the risk classes stay at five; arabic-home and family-meals are family tools with no lane.
- [How a feature with several change notes runs without Abdul](issues/19-multi-note-runs.md): `/build-feature` is a saved workflow; Abdul answers the stopping questions up front on one page; fresh agents per note implement, verify, review and merge, with a note check at strike two and a final check on the whole feature; state lives in git so any session restarts it; no ultra; model and effort set per role and compared by the audit.
- [How the careful lane keeps the test suite fast and trusted](issues/21-test-suite-speed.md): the implementer runs its own test files, each note's verifier one scoped run, and only the final verifier the full suite; a flaky file is rechecked alone and logged, never skipped; a suite budget per product puts raise-or-prune to Abdul in the next interview; one machine lock for full runs; one small suite script in the plugin.
- [Whether the build agents work test-first](issues/22-test-first.md): required in the careful lane and the fixer, the agent's choice in the fast lane; seams come from the core design's modules; a red check runs each new test on the code from before the note and refuses one that passes; the implementer runs it first, the verifier and the note check hook refuse; no mutation testing for now.
- [Which stacks the lanes support](issues/23-other-stacks.md): Abdul's own products only; work gets the toolbox and he adapts it there; tools stay named for Next.js and Supabase, with a port list in the spec; an MVP may use any stack, and the port happens at graduation; no rule on stack choice.
- [What the verifier checks in the browser](issues/24-browser-verification.md): a note that changes a screen names it and carries an end-to-end done check, both refused if missing; the verifier walks the note's new actions with hostile cases, and a fault case stays as a spec; a one-note change gets a fresh verifier; every core-design screen has a baseline, a new one taken at merge and approved by Abdul before the push; a new screen needs a prototype only for a new pattern; the fast lane marks new screens on its side-by-side page.
- [Walk two real cases through version 2](issues/25-walkthrough.md): a client's kit site in the fast lane and Orderflow's "Report a problem" in the careful lane, traced step by step; 23 open gaps went to eight grilling tickets, and the case for building in two stages heads the gap list.
- [Whether version 2 is built in two stages](issues/26-two-stage-build.md): two stages, fast lane first, careful lane and the switch second; nothing waits, so the kit site builds now and Orderflow's smaller features run on version 1, but multitenancy waits for the careful lane behind one small test feature; the evening check sorts from now; the switch needs no clean backlog; no MVP graduates before stage two, and waiting spends no keep.
- [How the ideas repo and the brainstorm routine run](issues/27-ideas-repo-and-routine.md): the stage-one build session creates `roufmlp/ideas` and the routine, which follows `routine.md` in that repo; every writer pushes there without asking; the page is a file marked `Opened:` on first reply; the audit table moves to a linked file; the cloud session reads the brief template from `agent-skills` and carries one ASD-STE100 line, not the writing rules.
- [How an MVP's limits and its end are recorded](issues/28-mvp-limits-and-record.md): one line per MVP, from an idea or a client, with its type and who it is for; keep has no limit; the day and page limits go; a site runs a shared `site-checks` set; the kit site waits for version 2 and graduates at delivery; the push check refuses history in skill files.
- [How a change goes live](issues/29-going-live.md): no agent touches production; the build session creates and deploys an MVP itself with the host's CLI, and each repo names its own host; the final verifier runs gate steps 1 to 7 on every change before the merge, on staging when there is one; migrations only add and go before the push; Abdul applies them, a `pre-push` hook refuses a push that carries an unapplied one, and the hard deny hook refuses agent commands that name production.
- [How a product graduates, stops or switches over](issues/30-graduate-stop-switch.md): one checklist file in the plugin, not a skill, started by Abdul typing `graduate` or `stop` in the product's repo; eleven steps in order, ticked in the brief; the session archives a stopped repo and Abdul does the host, keys and data; a client-named product gets a neutral name in the README; a fifth switch session writes Orderflow's core design from its routes and folders, with baselines from seed data; procurement's waits for its revamp.
- [What the interview settles before a run](issues/31-interview-before-a-run.md): `/build-feature` is a skill that runs the interview in Abdul's session, then starts the saved workflow from a clean one; the interview works on the feature branch in its own worktree, reads code through subagents and writes each done check's test; Abdul approves `changes/<feature>/plan.md`; the pre-run check runs before he sees it and again at each restart; access rules count as authentication; a merged feature or note is never built again.
- [What Claude Code offers to measure and cap a session's context](issues/34-context-size-facts.md): a hook can read a session's or a subagent's size from its transcript and block its tool calls, but cannot compact; one setting, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, compacts every model near 300k at about 333k, but cannot stop; today only Opus 5.5 has a 400k window, and a third of version 1's main sessions and a fifth of its implementers passed 300k.
- [What a run does when notes collide or fail](issues/32-collisions-and-failures-in-a-run.md): a note's migration is source and every check builds its database from empty; the merger numbers migrations at the merge and a check refuses duplicates; main merges into the feature branch before the final check; a third failure opens a short interview where Abdul changes or cuts notes, merged ones included; the final fix round gets a red check.
- [Where the note check lives, and baselines for changed screens](issues/33-note-check-and-changed-baselines.md): three git hooks in each graduated repo call one plugin script, installed at graduation and again by `prepare`; the branch names the note; git-shared-state-guard refuses skipped hooks; the red check runs on every merge into main; the final verifier retakes changed baselines and Abdul's push approves them; "Screens:" may name a route group.
- [How every version 2 session stays under 300k tokens](issues/35-context-size-rule.md): one setting compacts every session and agent at 400k for now, set in Abdul's settings, each plugin agent file and the routine's cloud environment; no hook; the audit counts compactions and start sizes per role, and Abdul lowers the window to 300k when sessions start smaller; the context hygiene section shrinks to eight lines.
- [What fills a session's first 100k tokens](issues/36-session-start-load.md): a main session starts at about 107k and a subagent at 90k to 100k; 77% of the tool-name list is three connectors (about 30k), then 34k of tool definitions, 12k system prompt and 10k skill listing; connectors off, skills name-only and `omitClaudeMd` bring a main session to about 59k and a subagent to about 35k, enough for a 300k window at 80% to 84% of version 1's work room; whether the controls reach the Desktop app's connectors is not found.

## Out of scope

- Rewriting the content of the design and code rules. The lanes only need to decide which files load where, which "Which steering files each lane loads, and the new CLAUDE.md" decided. The rewrite can follow the map as its own effort.
- An agent that takes Abdul's decisions from his preferences, a "CTO agent". It waits until three audits show how many decisions version 2 still gives him; [the audit ticket](issues/14-workflow-audit.md) adds that count.
- Designing Orderflow's multitenancy and its new features. That is product work on Orderflow; the map decides only which lane builds them and when, which [Whether version 2 is built in two stages](issues/26-two-stage-build.md) did.
- A careful lane for work projects in C#, .NET, Angular and MS SQL. The Copilot app at work takes no hooks, so the lane could not refuse, and Abdul adapts the toolbox there himself. [Which stacks the lanes support](issues/23-other-stacks.md) ruled it out.
