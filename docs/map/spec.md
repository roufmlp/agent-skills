# Workflow v2

Written on 2 November 2026 from the 36 tickets on [the workflow v2 map](map.md). Each section links the tickets that hold its detail, and a ticket wins over this page except where "Open at build time" says otherwise. [CONTEXT.md](../../CONTEXT.md) defines the terms.

Version 2 builds products at two speeds: a fast lane takes an idea through a prototype to a live MVP on test data, and a careful lane changes products that hold real data. It replaces version 1's chain, which took six weeks and 2,528 commits to build Orderflow, and aims at a real product every two to four weeks.

## The fast lane

An MVP is the smallest live app that runs its main flow end to end, and nothing real goes through it: no real customers or their data, no money that moves, no live keys. Claude interviews Abdul and writes a brief. A prototype in the real stack, on fake data, settles the look and behaviour, and once the person the MVP is for approves it, it becomes the first commit. One auto-mode session with `/goal` set to the done checks builds the rest and deploys to test environments itself. The MVP is done when it is live, its main flow passes in the browser, Abdul has used it once, and the person it is for approves a side-by-side page of prototype and MVP screenshots.

Detail: [What the fast lane does, from brief to done](issues/01-fast-lane-from-brief-to-done.md), [How an MVP's limits and its end are recorded](issues/28-mvp-limits-and-record.md), [How a change goes live](issues/29-going-live.md).

## The rule between the lanes

An MVP graduates when Abdul can name a person who will put real data into it within a week. Only he decides, graduation is one way, and no app skips the fast lane. Each brainstorm session gives every open MVP graduate, keep or stop, and a client's site graduates at delivery. Typing `graduate` or `stop` in the product's repo starts one checklist. Graduating runs the pre-launch gate, writes the core design with its checks and baselines, and switches the repo to the careful lane. Stopping archives it.

Detail: [What moves an MVP to the careful lane](issues/03-graduation-test.md), [How a product graduates, stops or switches over](issues/30-graduate-stop-switch.md).

## The careful lane

Every change starts as a change note: half a page that Claude writes in an interview with Abdul, naming the screens it touches, its risk classes and done checks that are commands. A one-note change runs as one `/goal` session. For a bigger change, `/build-feature` writes all its notes and their tests in one interview and asks Abdul to approve one page holding every question that could stop the run. Fresh agents then build, verify, review and merge each note without him, and a final verifier and reviewer check the whole feature.

Checks that refuse hold the lane, not instructions. A one-page core design lists each product's screens, patterns and modules, and a screenshot test, a check per pattern and import rules enforce it. A red check refuses a new test that already passes on the old code, a verifier tries to break each new action in the running app, and git hooks refuse a commit that changes a screen its note does not name. Risk-class changes (money, authentication, secrets, migrations, row writes) get `/code-review` at `max` effort, and steps 1 to 7 of the pre-launch gate run before anything reaches local main. No agent touches production: Abdul applies the migrations, which may only add, and he alone pushes. A smaller parallel-hunt runs on his command.

## The brainstorm session

At 09:00 UTC on the 1st and the 15th a cloud routine prepares one page in a private ideas repo, which also holds the idea log and the MVP list. Abdul opens the same session, gives each open MVP its result, and picks at most one of up to five ranked ideas, which leaves with a draft brief.

Detail: [How the brainstorm session works](issues/07-brainstorm-session.md), [How the ideas repo and the brainstorm routine run](issues/27-ideas-repo-and-routine.md).

## The audit

A local script summarises each week's sessions. On the 1st the brainstorm page links a table that tracks cost, tokens, decisions put to Abdul, interruptions, bugs, drift and growth, and lists proposals for his yes or no. The audit never removes anything. A budget in the push check refuses growth unless Abdul approves a raise.

Detail: [How a regular audit keeps the workflow small](issues/14-workflow-audit.md).

## One public repo, one install

Version 2 lands in the public `agent-skills` repo, with version 1 restorable at a `v1` tag. Private material lives outside it, and a `commit-msg` hook refuses client names and the home path, so nothing needs scrubbing. One command installs it, with no questions:

```
claude plugin install workflow --marketplace roufmlp/agent-skills
```

The `workflow` plugin carries Abdul's skills and agents, four hooks and the templates, and pulls in Matt Pocock's plugin for his 18 skills. Abdul's working copy is the plugin itself, and only a push to the `release` branch reaches anyone else. The GitHub Copilot app at work installs the same plugin and gets the skills and agents, never the hooks. The README opens on the cut: the pipeline that built Orderflow, measured and mostly cut.

Detail: [One repo that is safe to publish](issues/09-one-public-safe-repo.md), [How someone installs it](issues/10-install-path.md), [How the README tells the version story](issues/11-version-story.md).

## Every session

Every session and agent has a 400k window and compacts near 367k, and Abdul lowers the window to 300k once the audit shows sessions starting smaller. The code and design rules are skills, each product's `CLAUDE.md` names its lane, and one private file holds what only Abdul can do or decide.

## Open at build time

Writing this spec turned up points that the tickets leave open or answer two ways. This spec took the simplest default for each. On 2 November 2026 Abdul kept points 1 to 5 and 7 as written and overturned the default on point 6, so all seven are now decisions.

1. Git cannot hold a branch `feature/<name>` beside branches `feature/<name>/<nn>`, so the note branches that "How a feature with several change notes runs without Abdul" and "Where the note check lives, and baselines for changed screens" name cannot be made. The feature stays on `feature/<name>`, each note runs on `note/<name>/<nn>`, and the note check maps `note/<name>/<nn>` to note `<nn>`.
2. No ticket gives a session the job of writing Orderflow's "Production" line, its hosting block, its suite budget or its `migrate:production` script. Stage one writes the "Production" line, because the refusal it builds reads that line and Orderflow is live. At the switch the cleanup session adds the suite budget and the hosting block when it writes the lane block, and the fifth session also runs graduation step 8, which adds `migrate:production`. Abdul ruled on 3 November 2026 that Orderflow's line reads `Suite budget: 5 minutes`, not the 10 that "How the careful lane keeps the test suite fast and trusted" started it at: the suite read 550 s that day, so the first `/build-feature` interview asks the pruning question, which is what he wants it to do.
3. Stage one also builds the graduation checklist and the private pending file, since a client's site can graduate in stage one and any MVP can stop. "Whether version 2 is built in two stages" lists neither, yet the checklist's graduate and stop paths both write Abdul's steps to that file.
4. No ticket makes the `release` branch before the switch, so in stage one the routine reads the brief template from the private skills repo, where stage one builds it. The switch points `routine.md` at `release`.
5. "How a product graduates, stops or switches over" runs step 7, the git hooks, on a client's site that graduates in stage one. ## Trace 2: "Report a problem" on Orderflow, in the careful lane

Any signed-in person taps a speech bubble, types a sentence and sends it with a screenshot of the page behind. They see their own reports on a new My reports page and get an alert when one is settled, and the evening check reads every report through a database role of its own. Version 1 built it as 14 issues in 12.95 hours, with five migrations, and one issue took three strikes. In version 2 it is ten change notes: the four issues that let the evening check start fixes drop out, because that check now only sorts.

| Note | What it does | Migration | Waits for |
| --- | --- | --- | --- |
| 01 | The reports table, its row rules and two rights rows | adds a table | none |
| 02 | The bubble, the sheet, Send and the toast on every signed-in screen | none | 01 |
| 03 | A screenshot of the page behind the sheet | adds a column | 02 |
| 04 | One hint for a first-time phone user | adds a flag | 02 |
| 05 | A report sent offline is kept and sent once | none | 03 |
| 06 | The error page reports its own failure in one tap | none | 02 |
| 07 | The My reports page | none | 01 |
| 08 | The evening check's own database role | adds a role | 01 |
| 09 | An alert and a push when a report is settled | adds an alert reason | 07, 08 |
| 10 | One route for the evening check, behind its own secret | none | 08 |

0. **Where Orderflow starts.** The switch left its `CLAUDE.md` reading `Lane: careful`, with a 10-minute suite budget, a hosting block and a "Production" line. `docs/design.md` lists the 29 screens from the route tree and the modules from the folders under `src/`, with baselines from the local app on seed data, and `.githooks/` holds the three hooks (open point 2; [How a product graduates, stops or switches over](issues/30-graduate-stop-switch.md), [How the careful lane keeps the test suite fast and trusted](issues/21-test-suite-speed.md), [How a change goes live](issues/29-going-live.md)).
1. **The interview.** Abdul types `/build-feature report-a-problem`. No approved plan exists, so the skill interviews him in his own session, in a new worktree on `feature/report-a-problem`. Subagents read the code each note touches and hand back short summaries ([What the interview settles before a run](issues/31-interview-before-a-run.md)).
2. **The notes.** Claude writes the ten notes, each with a "Screens:" line, done checks, risk classes and "Waits for:". Note 02 names a route group, `Screens: all signed-in`, rather than every signed-in screen by name, and carries "Core design: adds the report bubble and sheet". Note 07 adds the My reports screen. Neither needs a prototype: My reports uses approved patterns, and the bubble adds a pattern but no screen ([What the verifier checks in the browser](issues/24-browser-verification.md)).
3. **The tests.** The interview writes the test behind each done check, Playwright specs for screens that do not exist yet among them, and commits each with its note. The pre-run check runs every done check on today's code and refuses one that passes, one with no test file, and a note that names a screen with no end-to-end check. 5. **The run.** In the clean session Abdul types the same command. It finds the approved plan and starts the `build-feature-run` workflow, which turns on keep-awake, and Abdul leaves the lid open on power ([What the interview settles before a run](issues/31-interview-before-a-run.md), [How a feature with several change notes runs without Abdul](issues/19-multi-note-runs.md)).
6. **Note 01.** On `note/report-a-problem/01` (open point 1), a Sonnet implementer works through `/tdd`, runs its own test files, then the red check: the old code and migrations go back, the test database is built from empty, and every new test must fail. An Opus reviewer reads the diff against the note and the core design, and the merger merges it into the feature branch ([Whether the build agents work test-first](issues/22-test-first.md)).
7. **Three at once.** Notes 02, 07 and 08 start together, the limit for one feature. Note 02's verifier tries to break the screens the note names: a reload with the sheet open, two fast taps on Send, the 390-pixel width, an empty box, a failed send. It compares every screen the note does not name against its baseline ([Where the note check lives, and baselines for changed screens](issues/33-note-check-and-changed-baselines.md)).
8. **A number clash.** Notes 03 and 04 both take the same next migration number on their own branches. At each merge the merger gives the migration the next free number, and a hook refuses two with the same number ([What a run does when notes collide or fail](issues/32-collisions-and-failures-in-a-run.md)).
9. **Note 03 fails.** The walk finds that the screenshot shows the top of a scrolled page: strike one. The reviewer finds the fix still draws from the top: strike two. The note checker finds the done check tested an unscrolled page, corrects it within what Abdul approved, and a third attempt starts. The reviewer then finds that Remove still works while Send is under way. The note fails, its branch stays, note 05 waits, and the rest carry on.
10. **The run stops short.** Eight notes merged, one failed, one not started. `report.md` says so, a phone notice goes out, and nothing merges to local main.
11. **A short interview.** Abdul types the command again. The skill finds the failed note and asks him to change or cut it. He drops Remove for now and approves the changed plan. Note 03 restarts with three new strikes and passes, and note 05 follows.
12. **The final check.** The merger brings local main into the feature branch. Holding the machine lock, the final verifier runs the full suite, the harness suite, the typecheck, every end-to-end spec and every baseline, retakes the baselines of every screen the notes named, and takes My reports' first. Then it runs steps 1 to 7 of the pre-launch gate. Orderflow names staging, so the verifier applies the five migrations there first, which rehearses them, and runs steps 1, 3, 4, 6 and 7 on a staging deploy of the branch ([How a change goes live](issues/29-going-live.md)).
13. **The final review.** An Opus reviewer at `max` effort, with the money, sign-in and secrets rubric, reads the whole diff against the brief, the core design and the ten notes, and refuses any migration that would break the code on `origin/main`. A finding goes to one fix round by a fresh implementer, whose new tests must fail on the commit the final check tested, and both final agents run again.
14. **Into main.** Main has not moved since the final check, which is what "fast-forward only" in "What a run does when notes collide or fail" asks, so the merger makes a `--no-ff` merge commit and the `pre-merge-commit` hook runs the red check for the whole feature. `report.md` gains a screens section: My reports at 390 and 1280 pixels, and each changed screen before and after.
15. **Abdul's side.** He reads the report and looks at the screens; his push will approve the new and changed baselines. He sets the two production secrets that the "Do" items name, runs `migrate:production`, which applies the five migrations and records the last in a git-ignored file, and pushes. The `pre-push` hook checks that file, and Vercel deploys.
16. **The audit.** The Sunday script picks up the run's time, tokens, strikes per role and any `DRIFT:` lines for the next monthly table ([How a regular audit keeps the workflow small](issues/14-workflow-audit.md)).
