# Research: how a Claude Code plugin installs, updates and fails

Sources checked: 2026-10-30

Docs: https://code.claude.com/docs/en/ . The old page names plugins, plugin-marketplaces, plugins-reference and discover-plugins now serve the pages plugins/overview, plugins/create-marketplace, plugins/manifest-reference and plugins/install. Changelog: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md (latest entry 2.1.314, 30 Oct 2026). Installed here: 2.1.306.
"Observed" means I ran the command on 2.1.306 with an empty HOME and no credentials. The docs do not say it. "Not confirmed" means the docs are silent or unclear.

## Q1. Which components can a plugin ship, and can it ship permissions or settings?
- Components: skills (`skills/<name>/SKILL.md`), agents (`agents/*.md`), hooks (`hooks/hooks.json`, same shape as the `hooks` key in settings.json), commands (older `commands/*.md`), MCP servers (`.mcp.json`), output styles (`output-styles/`). Also LSP servers, themes, monitors, workflows, `bin/` executables, channels and a `settings.json`. https://code.claude.com/docs/en/plugins/components
- Settings: a plugin `settings.json` is allowed, but only the keys `agent` and `subagentStatusLine` take effect. Every other key is dropped at load. So a plugin cannot ship `permissions` (allow, ask, deny) or `autoMode`. https://code.claude.com/docs/en/plugins/components#default-settings and https://code.claude.com/docs/en/plugins/manifest-reference#settings
- Other limits: plugin agents ignore the `permissionMode`, `hooks`, `mcpServers` and `initialPrompt` fields (https://code.claude.com/docs/en/plugins/components#agents). A `CLAUDE.md` at the plugin root is not loaded; write instructions as skills (https://code.claude.com/docs/en/plugins/components#skills). A skill can still pre-approve tools for one turn with `allowed-tools` (https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill).
- Status: confirmed.

## Q2. How is a plugin skill invoked, and how are plugin subagents named?
- Command form is `/<plugin>:<skill-directory>`. A frontmatter `name` replaces only the last part. The same page says the bare `/<skill>` also invokes the plugin skill unless another command has that name. https://code.claude.com/docs/en/skills#how-a-skill-gets-its-command-name
- Changelog 2.1.265 (8 Sep 2026): a slash command typed in the middle of a prompt now finds a plugin skill by bare name. Changelog 2.1.269 (11 Sep 2026): the Skill tool's "Unknown skill" error names the full name when a bare name matches one plugin skill. So Claude's own Skill tool calls probably need the full `plugin:skill` name. Not confirmed in the docs. https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md
- Subagent name is `<plugin>:<name>`; `agents/review/security.md` in `my-plugin` becomes `my-plugin:review:security`. Hooks see the scoped name as the agent type, not the bare name. https://code.claude.com/docs/en/plugins/components#agents and https://code.claude.com/docs/en/hooks#subagentstart
- Not confirmed: no doc line says the Agent tool's `subagent_type` takes the scoped name. Only `claude --agent <bare-name>` is documented to work, and only when the name is unique. An agent `name` may not contain `:` (https://code.claude.com/docs/en/sub-agents#supported-frontmatter-fields). https://code.claude.com/docs/en/sub-agents#invoke-subagents-explicitly
- Status: slash command confirmed; the literal `subagent_type` value and bare names in the Skill tool not confirmed.

## Q3. Commands to add a GitHub repo as a marketplace and install from it
- Two steps in a shell: `claude plugin marketplace add roufmlp/agent-skills`, then `claude plugin install <plugin>@<marketplace-name>`. In a session use `/plugin marketplace add ...` and `/plugin install ...`. https://code.claude.com/docs/en/plugins/publish#tell-users-how-to-install
- One step: `claude plugin install <plugin> --marketplace roufmlp/agent-skills` needs Claude Code 2.1.292 (6 Oct 2026) or later. It adds the marketplace with no confirmation, declares it in user settings, then installs at user scope. GitHub marketplaces need `git` on the machine (https://code.claude.com/docs/en/plugins/host-marketplace#host-your-marketplace). https://code.claude.com/docs/en/plugins/install#add-a-marketplace-and-install-in-one-command
- In a session, `/plugin install <plugin> --marketplace <source>` needs 2.1.275 (17 Sep 2026). It asks you to confirm the marketplace, then opens the plugin details so you pick a scope. That is not a one-step install. The changelog shows no `--marketplace` flag in 2.1.261. https://code.claude.com/docs/en/plugins/cli-reference#plugin-in-a-session and https://code.claude.com/docs/en/plugins/cli-reference#plugin-install
- One repo can be both. Put `.claude-plugin/marketplace.json` beside `.claude-plugin/plugin.json`, with one entry `{ "name": "<plugin>", "source": "./" }`. Keep the entry name equal to the manifest name. `claude plugin validate` prints the README install line to paste (2.1.295). https://code.claude.com/docs/en/plugins/publish#add-the-marketplace-file-to-your-repository and https://code.claude.com/docs/en/plugins/create-marketplace#keep-the-entry-name-and-the-manifest-name-the-same
- Name traps: the marketplace `name` cannot be `agent-skills` (reserved for Anthropic repos). Validate passes it and `marketplace add` refuses it; observed, and the docs say the same. A plugin `name` that starts with `claude-` or `anthropic-` fails validate. https://code.claude.com/docs/en/plugins/create-marketplace#problems-that-surface-when-you-add-or-install , https://code.claude.com/docs/en/plugins/marketplace-reference#reserved-names , https://code.claude.com/docs/en/plugins/manifest-reference#name
- Status: confirmed.

## Q4. Updates: auto-update, `claude plugin update`, pinning, the `version` field
- Auto-update is off by default for a third-party marketplace. It is on by default only for Anthropic's official marketplaces and marketplaces added from claude.ai. https://code.claude.com/docs/en/plugins/install#keep-plugins-updated
- Toggle: `/plugin`, Marketplaces tab, select the marketplace, Enable auto-update. Or set `"autoUpdate": true` on its `extraKnownMarketplaces` entry in any settings file; that setting wins over the toggle. `DISABLE_AUTOUPDATER`, `DISABLE_UPDATES` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` switch it off unless `FORCE_AUTOUPDATE_PLUGINS=1`. https://code.claude.com/docs/en/plugins/loading#when-auto-update-runs and https://code.claude.com/docs/en/settings-reference#extraknownmarketplaces
- Timing: after the first message, a random delay of up to 10 minutes, then it refreshes the marketplace and updates plugin files on disk. The running session keeps the old version and shows "Plugin updated ... Run /reload-plugins to apply". Same loading page.
- `claude plugin update <plugin>@<marketplace>` installs the latest version the marketplace offers; it applies at the next session or `/reload-plugins`. It prints "already at the latest version" when the computed version did not change. There is no update-all command; `claude plugin marketplace update` with no name refreshes listings only. https://code.claude.com/docs/en/plugins/cli-reference#plugin-update and https://code.claude.com/docs/en/plugins/install#update-plugins-now
- Pinning: yes. `github`, `url` and `git-subdir` plugin sources take `ref` (branch or tag) and `sha` (full commit). The marketplace itself pins with `owner/repo#<tag>` at add time. A `"./"` entry has no `ref` or `sha` field. https://code.claude.com/docs/en/plugins/marketplace-reference#plugin-sources and https://code.claude.com/docs/en/plugins/host-marketplace#hold-users-on-one-version
- The `version` field gates updates. Version is manifest `version`, else entry `version`, else a commit SHA (for a relative-path entry in a git marketplace, the commit of the installed directory). Claude Code replaces the cached copy only when the version changes. A fixed `version` with new commits leaves users on the old copy; omit `version` to track every commit. https://code.claude.com/docs/en/plugins/loading#versions-and-updates
- Status: confirmed.

## Q5. Local development: `--plugin-dir`, local-directory marketplace, reload
- `--plugin-dir <dir>` loads a plugin directory (or .zip) for one session only, as `<name>@inline`. It writes nothing to settings, loads in place, and silently replaces an installed plugin of the same name. `CLAUDE_CODE_PLUGIN_DIRS` (2.1.280, 22 Sep 2026) does the same without a flag. https://code.claude.com/docs/en/plugins/cli-reference#flags-that-load-a-plugin-for-one-session and https://code.claude.com/docs/en/plugins/create#load-plugins-from-an-environment-variable
- Local-directory marketplace: a plugin with a relative-path source loads in place. Edits apply at the next session start or `/reload-plugins`, with no version bump, and hooks get `CLAUDE_PLUGIN_ROOT` = the source directory. Every other marketplace plugin, including one from a GitHub marketplace, is copied to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. https://code.claude.com/docs/en/plugins/loading#in-place-and-copied-plugins and https://code.claude.com/docs/en/plugins/create-marketplace#test-an-edit-to-a-plugin
- `/reload-plugins [--force]` exists. It applies installs, updates, enables and on-disk edits made since the session started, and prints counts and load errors. It also runs in desktop and `-p` sessions (2.1.260+). https://code.claude.com/docs/en/plugins/cli-reference#reload-plugins
- Also in place: a folder with `.claude-plugin/plugin.json` under `~/.claude/skills/<name>/` loads every session as `<name>@skills-dir`, with no install step. https://code.claude.com/docs/en/plugins/create#make-a-plugin-load-in-every-session
- For his case (deduction): a user cannot register one marketplace name from two sources, so on his machine the GitHub source or the working copy holds the name, not both. https://code.claude.com/docs/en/plugins/marketplace-reference#marketplace-file and https://code.claude.com/docs/en/plugins/troubleshooting#marketplace-name-is-already-added-from-a-different-source
- Status: confirmed.

## Q6. Marketplace in `extraKnownMarketplaces` and plugin in `enabledPlugins` in `~/.claude/settings.json`
- Documented: plugins load from disk at session start. After start, Claude Code checks declared marketplaces in the background. A declared marketplace that is not on disk is cloned, then plugins reload and enabled plugins that are not cached are downloaded. No prompt is documented. https://code.claude.com/docs/en/plugins/loading#plugins-and-marketplaces-that-arent-on-disk-at-session-start
- A plugin from an external source is fetched only when user settings, an untracked `.claude/settings.local.json`, `--settings` or managed settings set it to `true`. A plugin set only in a committed project `.claude/settings.json` is not fetched, except a relative-path plugin of the marketplace. https://code.claude.com/docs/en/plugins/loading#enabled-in-project-settings-but-not-installed
- Managed settings with the same two keys: the docs say Claude Code registers the marketplace and installs the plugins when the user next starts a session. https://code.claude.com/docs/en/plugins/org#require-a-marketplace-and-its-plugins . Changelog 2.1.144 fixed "not cached" errors for plugins enabled in your own settings on a fresh machine.
- `claude plugin marketplace add` writes `extraKnownMarketplaces` into user settings, and install writes `enabledPlugins`, so a git-tracked settings file can carry both keys. https://code.claude.com/docs/en/plugins/loading#check-which-stage-a-plugin-reached and https://code.claude.com/docs/en/plugins/install#choose-an-install-scope
- Not confirmed: whether the first session already shows the plugin or needs `/reload-plugins` or a restart. In `-p` and CI runs the install is in the background; `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1` makes the run wait (documented for managed and repository settings). https://code.claude.com/docs/en/plugins/org#when-each-surface-applies-the-plugin-keys
- Status: confirmed that it installs by itself, with no prompt documented; first-session timing not confirmed.

## Q7. Plugin hooks: activation, trust, auto mode, desktop, cloud, path variables
- Active when the plugin is enabled, with no settings.json edit. Claude Code registers them when the session loads the plugin, and they merge with user and project hooks. A settings hook moves into `hooks/hooks.json` unchanged. https://code.claude.com/docs/en/plugins/components#hooks and https://code.claude.com/docs/en/hooks#hook-locations
- Trust: no separate approval step for hooks is documented. Documented gates: a trust warning on the plugin details pane before install; installing also enables the plugin; a project-scope plugin loads only after workspace trust. Plugin hooks run with your full user permissions, outside the sandbox. https://code.claude.com/docs/en/plugins/security#understand-what-a-plugin-can-do , https://code.claude.com/docs/en/plugins/security#trust-warning-before-you-install , https://code.claude.com/docs/en/plugins/loading#trust-check-and-component-limits-for-repository-plugins . Not confirmed: the workspace-trust gate is documented for settings-file hooks, not for user-scope plugin hooks. https://code.claude.com/docs/en/hooks#workspace-trust
- Auto mode: PreToolUse hooks run before the permission step. A hook cannot override deny or ask rules, and the page says this covers hooks in settings files and in a plugin's `hooks/hooks.json`. Auto mode still shows prompts that a hook forced; changelog 2.1.211 fixed a hook `ask` being overridden. No doc says plugin hooks differ from settings hooks in auto mode. https://code.claude.com/docs/en/permissions#precedence-among-rules-hooks-and-mods
- Desktop: the CLI, desktop local sessions and VS Code read the same settings files, so a user-scope plugin is available in all three. That plugin hooks run there is an inference; no doc states it for hooks. Plugins are not available in WSL sessions. https://code.claude.com/docs/en/plugins/install#choose-an-install-scope and https://code.claude.com/docs/en/desktop#install-plugins
- Cloud: a cloud session does not load plugins from user settings or from the repo's `.claude/settings.json`, so those plugin hooks do not run. Hooks written in the repo's own `.claude/settings.json` do, in a one-repository session. https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup
- `${CLAUDE_PLUGIN_ROOT}` is the plugin install directory: a per-version cache directory that changes on update (the source directory for in-place plugins). Do not write state there. `${CLAUDE_PLUGIN_DATA}` is `~/.claude/plugins/data/<id>/`, kept across updates and deleted at last-scope uninstall unless `--keep-data`. Both work in skills, agents, hook commands and MCP/LSP configs, and hook processes get them as environment variables. Quote `${CLAUDE_PLUGIN_ROOT}` in shell-form commands; exec form (`command` plus `args`) needs no quotes. https://code.claude.com/docs/en/plugins/components#reference-plugin-paths-and-store-data
- Status: active-on-enable, cloud and path variables confirmed; user-scope plugin trust step, desktop hooks and any auto-mode difference not confirmed.

## Q8. Health checks: validate, eval, /doctor, /skill-doctor, load errors
- `claude plugin validate <path> [--strict] [--json]` is a static check of the plugin manifest, marketplace manifest, and skill, agent and command files. Exit 0 pass, 1 fail, 2 validator error; the docs call it usable by a CI job. Docs are silent on credentials. Observed with no credentials: it ran, exit 0 for a good plugin and exit 1 for an invalid `hooks/hooks.json`. https://code.claude.com/docs/en/plugins/cli-reference#plugin-validate
- `claude plugin eval` (2.1.269, 11 Sep 2026) runs eval cases in isolated `claude -p` sessions with and without the plugin and scores them; exit codes are CI-ready. It needs model credentials such as `ANTHROPIC_API_KEY` and costs money, so it is not key-free. https://code.claude.com/docs/en/plugin-evals#requirements and https://code.claude.com/docs/en/plugin-evals#run-evals-in-ci
- `/doctor` is an in-session skill: a setup checkup (install, settings, unused skills, MCP servers and plugins, slow hooks, CLAUDE.md, permissions, usage) that proposes fixes and asks first. `claude doctor` in a shell prints read-only install and settings diagnostics. https://code.claude.com/docs/en/skills#check-your-setup-with-/doctor and https://code.claude.com/docs/en/cli-reference
- `/skill-doctor` reports each skill's context cost and use count and lists unused skills and plugins. Docs say it needs 2.1.252 or later; the changelog lists it as added in 2.1.261. It needs feature-flag fetching, so it can be missing in a clean CI container. It is a usage report, not a correctness check. In `-p` it prints text. https://code.claude.com/docs/en/skills#find-unused-skills and https://code.claude.com/docs/en/env-vars#features-that-need-feature-flag-fetching
- CI without an API key: validate yes (observed). `claude --plugin-dir . plugin list` prints `Status: ✔ loaded` or `✘ loaded with errors` plus the error (observed with no credentials; the docs describe the command). Eval no. `/doctor` and `/skill-doctor` not confirmed. Any CI job first needs the Claude Code CLI installed (https://code.claude.com/docs/en/setup); no doc covers `plugin validate` inside a GitHub Action. https://code.claude.com/docs/en/plugins/create#test-and-debug
- Startup errors: no startup banner for plugin load errors is documented. Errors show in the `/plugin` Errors tab, `claude plugin list`, the `/reload-plugins` summary ("N errors during load"), and a failed hook shows `<Event> hook error` in the transcript. `/doctor` lists some plugin warnings (changelog 2.1.140). Changelog 2.1.183 removed the startup "setup issues" line in favour of `/doctor`. https://code.claude.com/docs/en/plugins/troubleshooting#plugin-doesnt-appear-or-its-skills-dont-show-up
- Status: validate, eval, doctor and skill-doctor behaviour confirmed; keyless CI use of the doctor commands and a startup error banner not confirmed.

## Q9. Desktop app, cloud sessions and scheduled cloud routines
- Desktop app, local and SSH sessions: yes. The terminal, desktop local sessions and VS Code read the same settings files, so a plugin installed at user scope in the CLI is available. The Cowork part of the app takes plugins from the claude.ai account, not from `~/.claude`. https://code.claude.com/docs/en/plugins/install#choose-an-install-scope and https://code.claude.com/docs/en/desktop#install-plugins
- Cloud sessions: no for plugins from user settings, and no for plugins declared in the repo's `.claude/settings.json` (`enabledPlugins`, `extraKnownMarketplaces`). What loads: the repo's committed `.claude/skills/`, `.claude/agents/` and `.claude/commands/`; hooks and permission rules in its `.claude/settings.json` (one-repository session); plugins from server-managed settings (organizations); plugins turned on for the claude.ai account (shown as `name@synced`, changelog 2.1.239). https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup and https://code.claude.com/docs/en/plugins/install#install-a-plugin
- Scheduled cloud tasks (routines): each run is a fresh cloud session that clones the repo. Skills committed to the repo load; a skill only in `~/.claude/skills/` is reported as not found. The routines page does not mention plugins. Changelog 2.1.314 (30 Oct 2026): cloud runs now load plugins enabled on the claude.ai account. https://code.claude.com/docs/en/routines and https://code.claude.com/docs/en/skills#use-skills-in-cowork-and-cloud-sessions
- Not confirmed: how a solo user puts their own repo plugin on a claude.ai account. The code.claude.com pages point to claude.com pages for that.
- Status: confirmed for desktop and for repo-settings plugins in cloud; plugin loading in routines rests on the changelog only.

## Q10. Symlinks without plugins
- Skills: yes. A `<skill-name>` entry under `~/.claude/skills/` (also the enterprise and project locations) can be a symlink to a directory elsewhere. Claude Code reads `SKILL.md` from the target and loads the skill once even if several links point at it. https://code.claude.com/docs/en/skills#choose-where-skills-load
- Not confirmed: live reload when the edit is made inside the target directory. The docs promise live reload for skills that sit under `~/.claude/skills/`, and say nothing about link targets. Also, `claude plugin validate` does not follow symlinks inside the directory it checks. https://code.claude.com/docs/en/skills#edit-a-skill-during-a-session and https://code.claude.com/docs/en/plugins/cli-reference#validate-a-directory
- Agents: not confirmed. The sub-agents page says `~/.claude/skills/workflow/agents/` is scanned recursively and says nothing about symlinks; the changelog has no agent-symlink entry. https://code.claude.com/docs/en/sub-agents#choose-the-subagent-scope
- Status: skills confirmed; agents not confirmed.

## Q11. Uninstall
- `claude plugin uninstall <plugin>@<marketplace> [--scope user|project|local] [--keep-data] [--prune]`, or Uninstall on the `/plugin` Installed tab, removes the plugin from that scope. At the last scope it also deletes the plugin's stored options and secrets and `~/.claude/plugins/data/<id>/`, unless `--keep-data`. Auto-installed dependencies stay until `claude plugin prune`. https://code.claude.com/docs/en/plugins/cli-reference#plugin-uninstall
- Cached files stay under `~/.claude/plugins/cache/` for 14 days, then a background sweep removes them. https://code.claude.com/docs/en/plugins/loading#cleanup-of-previous-versions and https://code.claude.com/docs/en/plugins/security#remove-a-plugin-you-no-longer-trust
- settings.json: uninstall checks that the scope's settings no longer switch the plugin on. If it cannot confirm this, it stops with "was not uninstalled" and names the settings file (changelog 2.1.282). For a plugin the project enables, "Disable for me" writes `false` in `.claude/settings.local.json` and "Uninstall for everyone" removes the entry from `.claude/settings.json`. `claude plugin marketplace remove` uninstalls every plugin of that marketplace and removes their `enabledPlugins` entries. https://code.claude.com/docs/en/plugins/install#uninstall-a-plugin-the-project-enables and https://code.claude.com/docs/en/plugins/install#manage-marketplaces
- Not confirmed: whether a user-scope uninstall deletes the `enabledPlugins` key or sets it to `false`, and whether the `extraKnownMarketplaces` entry stays. No doc says uninstall edits it. If a git-tracked settings file still lists both keys as `true`, Q6 suggests the next session installs the plugin again (deduction).
- Status: data and cache removal confirmed; settings.json residue not confirmed.
