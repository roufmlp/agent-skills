# How someone installs it

## Question

What does the one install command do, for Abdul on a new machine and for a friend on theirs? Pin down what it installs (skills only, or hooks too), what it asks, how it updates, and how Abdul learns that it has stopped working. The bar: under ten minutes, with nobody sitting beside them. "What the careful lane keeps" left 23 skills and 6 hooks, one of them (pilot-database-guard) private. "One repo that is safe to publish" made `agent-skills` the public repository, which Abdul works in directly from the switch on, and left this ticket to decide where that working copy sits. Its `commit-msg` hook runs only once `core.hooksPath` points at it, so Abdul's install has to set that. The list of private names, the approval guard on it, pilot-database-guard and the skills that do not ship, such as writingrules, stay in `~/.claude/`, outside the install.

## Answer

Version 2 installs as a Claude Code plugin, and the public repository is also its marketplace. A friend runs one command and answers no questions:

```
claude plugin install workflow --marketplace roufmlp/agent-skills
```

It needs Claude Code 2.1.292 or later, and git. The plugin is called `workflow` and the marketplace `roufmlp`, because Anthropic reserves `agent-skills` as a marketplace name. Claude Code copies the files, switches the hooks on without touching the friend's settings, and removes it all with one uninstall. A clone and a script was rejected: the script would have to write hook entries into a settings file the friend owns, then undo them on removal. The facts behind this ticket are in [the plugin research](../research/10-install-path.md).

The plugin carries 22 skills, 7 agents and 4 hooks: coderules-gate, git-shared-state-guard, machine-wide-kill-guard and headless-chrome-guard. The hooks ship because the README's story is scripts that refuse what reminders failed to stop. machine-preflight stays in `~/.claude/` beside pilot-database-guard. Its limits, 5 days of uptime or 8 swapfiles, come from one panic on Abdul's Mac, and it calls a macOS-only command. writingrules does not ship.

A plugin cannot carry permission rules or auto-mode settings: Claude Code drops every plugin setting except `agent` and `subagentStatusLine`. So a refusal that ships stays a hook. The live-key hard deny and the approval guard on the private-name list stay in Abdul's private settings, and the move into `autoMode.hard_deny` or a deny rule that "What the careful lane keeps" allowed now applies to private refusals only.

The plugin changes how things are named. A skill's full name is `/workflow:grilling`, and the bare `/grilling` still works while no other skill has that name. Agents become `workflow:parallel-hunt-finder` and so on, so the build rewrites the nine lines in parallel-hunt and panel-review that name an agent. None of the seven agents uses the fields a plugin agent ignores (`permissionMode`, `hooks`, `mcpServers`).

The hooks need Python 3. macOS has it with the command line tools that git already needs, and Linux has it. On Windows, Claude Code shows a hook error until Python is installed but blocks nothing. The README says so.

Abdul's working copy is the plugin. He clones the public repository into `~/.claude/skills/workflow/`, and Claude Code loads a plugin folder there directly at every session start, with no install step. A merge to local `main` is live for him at his next session, as a merge to master is today. Installing from GitHub like a friend was rejected, because every fix would wait for a push and every push waits for Abdul. The price is that he never runs the published install at home. The check below covers it, and his machine at work runs it every day. On a new machine he takes three steps: clone `claude-config` into `~/.claude`, clone the public repository into `~/.claude/skills/workflow/`, and set `core.hooksPath` there so the `commit-msg` hook from "One repo that is safe to publish" runs. `claude-config` then tracks the private skills in `~/.claude/skills/` and ignores `workflow/`.

Only releases reach other machines. Abdul pushes to `main` as often as he likes, and `git push origin main:release` makes a release. `release` is the default branch on GitHub, so the install command names no branch and always takes the latest release. A GitHub branch rule on `release` refuses a commit that has not passed the check on `main` first. The plugin carries no version number, so each release counts as a new version. A version number was rejected because Claude Code compares it only for a plugin already installed: a friend who installs between releases would get the latest push, mistakes included. Plugins from a marketplace outside Anthropic do not update by default, so the README tells a friend to switch auto-update on once in `/plugin`. From then on, each release reaches them a session or two later. The switch session sets the default branch and the branch rule, with Abdul's approval.

A GitHub Action checks the plugin on every push and once a week. With no API key, it installs the latest Claude Code and runs `claude plugin validate`, a load check and the hook tests. Each week it also runs `claude plugin eval` with an Anthropic API key from the repository's secrets: one case per hook asks for the refused command and passes only if the hook refuses it. That weekly run catches the failure nobody would see. When Claude Code renames a tool, a hook matching the old name stops firing and reports no error. This has happened before, which is why the version 1 hooks match both `Task` and `Agent`. The build measures what the weekly run costs. A failed run sends GitHub's failure email, and the brainstorm page carries one line, "Install check: passing" or the check that failed. The routine therefore reads the public repository's latest result as well as the ideas repo.

At work Abdul uses the GitHub Copilot app, on a Windows machine where he cannot install .exe files but may add skills. The app adds a marketplace from a GitHub repository with no installer, and Copilot accepts the Claude Code plugin format, so the app installs the same `workflow` plugin from `release` and updates it automatically once that option is on. At work the app gets the toolbox: the skills and agents. The hooks must not run there. In the app a hook that cannot start blocks every tool call, Python on Windows needs an .exe, and two of the four hooks only look for macOS or Unix commands anyway. The build makes sure the app on Windows never starts them. A PowerShell copy of each hook was rejected: it doubles the hook code, and only two of the four hooks have anything to catch on Windows. Some skills depend on Claude Code features Copilot lacks, such as the agent types parallel-hunt starts, and may fail there. If his employer blocks outside marketplaces, the app can still install a single skill from a GitHub folder, without automatic updates. The first install at work settles both. The Copilot documents confirm the plugin format for Copilot CLI, which the app is built on; the facts are in [the Copilot research](../research/10-copilot-support.md).

The switch also tags and archives `claude-agents`, the version 1 repository behind `~/.claude/skills/workflow/agents/`. "One repo that is safe to publish" named only `claude-skills-live` and `claude-config`, and a rollback needs all three. In version 2 the agents live in the plugin.
