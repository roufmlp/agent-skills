# Build feature

One command, two halves. The plan check decides which one runs, every time:

```
python3 ~/.claude/skills/workflow/lib/plan_check.py plan <name> --tree <feature worktree>
```

| It prints | Exit | Road |
| --- | --- | --- |
| `plan: approved <date> at <commit>` | 0 | The run |
| `INTERVIEW: no plan` | 2 | The interview |
| `INTERVIEW: failed notes <nn>` | 2 | The short interview |
| `REFUSED:` naming no Approved line, or a change after the approval | 3 | An interview that did not end. Carry on at step 7 of the interview. |
| Any other `REFUSED:` | 3 | Stop and show the human the line. |

The name is lower-case letters, digits and hyphens. The session's folder is the product repo, whose `CLAUDE.md` reads `Lane: careful`. The feature lives in its own worktree, `<repo>/.claude/worktrees/feature-<name>`, on the branch `feature/<name>`: when the worktree exists, run the check there; when only the branch exists, add the worktree first (`git worktree add .claude/worktrees/feature-<name> feature/<name>`); when neither exists, run the check in the repo, where it finds no plan, or a merged report on main.

Everything on the page and in the notes is written for the build agents, after reading the code: `templates/change-note.md`, `templates/plan.md` and `templates/report.md` in the skills repo are the three shapes, and the hooks, the note check and the plan check read them line by line. Terms: CONTEXT.md in the skills repo (change note, feature plan, done check, cut, red check, hostile walk).

## The interview

The human is at the keyboard. The session stays small: subagents read the code and hand back summaries, and every answer he gives is written to the page at once, so a compaction loses nothing. Ask him only the questions of the four kinds; every other fork is a default, written into the note it belongs to.

1. **The worktree.** From local main (`main` or `master`): `git worktree add .claude/worktrees/feature-<name> -b feature/<name> main`. Every file this interview writes goes there, and the run starts there. Done when `git -C <worktree> branch --show-current` prints `feature/<name>`.
2. **The feature.** One question, before any reading: what the feature does, in a few sentences, if the command did not say. Write it as the plan's first paragraph, `changes/<name>/plan.md` from `templates/plan.md`, title and `Feature:` line filled. Done when the paragraph is on the page.
3. **The code.** Read `BRIEF.md` and `docs/design.md` yourself. For each screen, module or table the feature touches, one Explore subagent with a narrow brief returns at most fifteen lines: the files, the pattern they use, the tests beside them, the migration that owns the table. Keep the summaries, never the files. Done when every screen and table the feature names has a summary.
4. **The notes.** Cut the feature into change notes, `changes/<name>/<nn>-<slug>.md` from `templates/change-note.md`, numbered from `01`. Each note is one fresh Sonnet implementer's session: half a page, real button, label and file names from the summaries. A note that adds a shared pattern goes first, and every note that uses it names it on its `Waits for:` line. A migration only adds. `Risk:` names each of money, authentication, secrets, migration and row writes the note touches; a right, a role or a row policy is authentication. `Screens:` names the table's screens, `all <group>`, or `none`, and a note that names a screen carries one end-to-end done check, a Playwright spec, per screen. A note that adds a screen adds its row to the screens table of `docs/design.md` in the same commit and carries a `Core design:` line, since the note check reads the table from the index and guards that file. Every done check is one command and what its pass proves. Done when `plan_check.py notes <name> --static` prints `ok` for every note except the test files, which step 5 writes.
5. **The tests.** For each done check, write its test file and name it in the note's `## Tests` part: a Playwright spec against a screen that does not exist yet, from the button and label names in the note and the core design; a vitest file for logic. A test that protects behaviour the note does not change starts its title with `keeps:`. Commit each note with its tests, `note <nn>: <title>`; the hooks fire, and notes and tests are not guarded paths. Take no baseline. Done when every note is committed and `plan_check.py notes <name> --static` prints `ok` for every note.
6. **The pre-run check.** `plan_check.py notes <name>`, which runs every done check on today's code. The Playwright checks need one build of the app, a few minutes, spent now rather than after the human leaves. Fix each `REFUSED` line in the note or its test and commit, then run it again. When it prints `PRUNING:`, the suite is over budget: add the `[pruning]` question to the page. Done when the check exits 0.
7. **The page.** Fill the plan: the notes table, the order in rounds of three at most, and the questions, one line each, of the four kinds and the pruning question when step 6 asked for it. Core design: each pattern a note adds or each screens rewrite, with the check behind it. Migration: each one, and that it only adds. Money or access rules: each price, right, row policy, role or secret a note changes. Data leaving: each route, webhook, push or email format a note commits. Show the human the page, then put the questions one at a time, and write `Answer:` under each the moment he gives it. Done when `plan_check.py plan <name>` names no unanswered question.
8. **The approval.** When the human writes `approve`, append `Approved: <today>` to the page and commit the page and the notes together, `plan: <name> approved`. Run `plan_check.py plan <name>`; it must print `plan: approved`. Then tell him, in two lines: `/clear`, and type `/build-feature <name>` again. End the session there; the clean session sees the approved plan and runs. Done when the check printed `plan: approved` and the two lines are on screen.

## The short interview

The report on the feature branch shows a failed note (three strikes) or a note stopped on a question of the human's kind (a done check that passed before the work, an implementer's or the note checker's `stopped:`); the plan check prints `INTERVIEW: failed notes` for both. The run does not merge and the final check does not run until this ends. The interview owns the report rows of the notes it touches; the merger owns the rest.

1. **The failure.** Read `changes/<name>/report.md` and each failed note's last reject report, named in its row. For each failed note, tell the human in two lines what failed, then offer two roads: change the note, or cut it. He may also cut a note that already merged, to ship it later; the merger reverts its merge commit on the feature branch.
2. **A cut.** Move the note to `changes/<name>/cut/` and delete the test files its `## Tests` part names, in one commit, since the hook refuses a deleted test a live note still names (the interview committed them with the note, and a revert of the note's merge brings them back as they were: in the rehearsal a cut note's test read a table no migration created, and the final check failed on it). Add its line under `## Cut` on the page, and set its report row to `cut <date>`. A cut note that had merged is reverted here, in this session: `git revert -m 1 <its merge commit>` on the feature branch (the merger merges every note with `--no-ff`, so the commit has two parents), and the `## Cut` line names the revert commit. A note that waits for a cut note, or uses its work, is cut or changed too: list those before he approves. `plan_check.py notes <name>` refuses a `Waits for:` naming a note that is gone.
3. **A change.** Edit the note and its tests within what he says, commit, and run `plan_check.py notes <name> --only <nn>` until it prints `ok`. Set its report row to `not started`: the note starts again with three new strikes.
4. **The approval.** When he writes `approve`, append a new `Approved: <today>` line, commit the page, the notes and the report together, and run `plan_check.py plan <name>`; it must print `plan: approved`. Tell him to `/clear` and type the command again, and end the session.

## The run

The plan check printed `plan: approved`. The session starts the `build-feature-run` workflow and watches it; the seven roles in `~/.claude/skills/workflow/agents/build-feature-<role>.md` do the work, and `changes/<name>/report.md` on the feature branch is the ledger the merger keeps. Nobody answers a question mid-run: a note that needs the human stops, and the question goes under "Decide" in `~/.claude/pending.md`.

1. **The pre-run check.** `plan_check.py notes <name> --tree <worktree> --only <every note whose report row is not started>`. A note whose done check now passes stops: write its row as `stopped: done check passes before the work` in `changes/<name>/report.md` on the feature branch (from `templates/report.md` when the file does not exist yet), commit it as `report: note <nn> stopped`, and put the question under "Decide" in `~/.claude/pending.md` under the `questionrules` skill. The notes that wait for it wait, and the rest run. Done when the check exits 0 or every refused note has its row.
2. **The arguments.** `python3 ~/.claude/skills/workflow/lib/feature_run.py args <name> --tree <worktree>`, with `--role <role>=<model>:<effort>` for each override in the command (`implementer=opus:medium`). It prints the JSON the workflow takes: the note graph from the `Waits for:` lines, each note's state from the report, the lines an earlier run left in the report, the paths, the models and efforts, and `started` from the clock; never type a time by hand. For each note whose `fresh` is `true`, remove its old worktree and branch now, from this session: `git -C <repo> worktree remove --force <worktree>` and `git -C <repo> branch -D <branch>`, then `git -C <repo> worktree prune`. The merger's spawn cannot: the auto-mode classifier refuses `git worktree remove --force` as irreversible, and in the rehearsal that stopped a note as `stopped: worktree:`, which this removal and a restart clear. A `REFUSED:` line stops here. Done when the JSON is on screen.
3. **The start.** `mcp__ccd_host__request_keep_awake` with `until: session_idle`, then the `Workflow` tool with `scriptPath` `~/.claude/skills/workflow/workflows/build-feature-run.js` and `args` set to that JSON as an object, never as a string. Keep the task id and the transcript dir the result gives. The script runs each note in its own worktree, `<repo>/.claude/worktrees/note-<name>-<nn>` on `note/<name>/<nn>`, three notes at once, a verifier and a reviewer per attempt, the note checker at strike two, three strikes to fail, and one merger at a time; every reject report goes under `.git/build-feature/<name>/`, never under `changes/`. Done when the result says the run started.
4. **The watchdog.** `ScheduleWakeup` for 1,800 seconds, prompt `watch build-feature <name>`. On each wake: when the task has finished, go to step 5. Else read the newest change time among `<worktree>/changes/<name>/report.md` and every file under the transcript dir. Moved within the last 30 minutes: schedule the next wake. Nothing moved: `TaskStop` the task, take the last line of the newest `agent-*.jsonl` as the error, send `PushNotification` `<name>: nothing moved for 30 min: <error>`, and start again from step 1; a new run reads the report and skips the merged notes. Give up after three starts in a row with no newly merged note, or after three days: notify and end the session. A start in which no agent returned any result (an outage) does not count toward the three; only the three days end a session that never recovers.
5. **The end.** The result carries `state` (`merged` or `stopped`), `notes`, `halted` and `notice`. Send `notice` with `PushNotification`. Fill the tokens and cost cells: `python3 ~/.claude/skills/workflow/lib/feature_run.py roles <transcript dir> --report <report path>`, on the feature worktree, or on local main when the feature merged, and commit it as `report: <name> roles`. `halted` names a role that returned no result twice, a usage limit the runtime stopped waiting for or an outage: wait for the reset when the task panel named one; when none is named (an outage), `ScheduleWakeup` for 1,800 seconds and start again on the wake; then start again from step 1 as one of the three. A `stopped` run with a `failed` row, or a `stopped:` row of a question's kind, waits for the human: the next `/build-feature <name>` opens the short interview; a `stopped: worktree:` row starts again like `API errors`. A run stopped by the final check (`## Final check` lists findings and no row failed) waits for a fix: a finding in the feature is fixed on the feature branch in its own session; a finding on main is fixed on main; then the next `/build-feature <name>` passes the plan check, skips the merged notes, brings main in and runs the final check and the merge again. Done when the notice was sent and the roles cells are filled.

The runtime itself waits for a usage-limit reset twice and restarts an agent whose output stops up to five times; the script requeues a note whose agent returned no result once, then stops the run. The allow rules the build agents need are in the global settings, `permissions.allow`; the list is `build-feature/allow-rules.md`, and the first long run is the place to add what still prompts.

A one-note change never uses this skill. It runs as one `/goal` session, and that session runs `plan_check.py notes changes/<nn>-*.md` once before it builds; a refusal stops it.
