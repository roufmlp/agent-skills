# Build feature

One command. The plan check decides which road it takes, every time:

```
python3 ~/.claude/skills/workflow/lib/plan_check.py plan <name> --tree <feature worktree>
```

| It prints | Exit | Road |
| --- | --- | --- |
| `plan: approved <date> at <commit>` | 0 | The run. When the line ends `waiting for <name>: <nn>` and the human typed the command, put those notes to him first (The rulings, step 7). |
| `INTERVIEW: no plan` | 2 | The interview |
| `RULING: notes <nn> (<state>)` | 2 | The rulings |
| `GATE: <n> ruling(s) ...` | 2 | The gate |
| `REFUSED:` naming no Approved line | 3 | An interview that did not end. Carry on at step 7 of the interview. |
| `REFUSED:` naming a change after the approval | 3 | A change no ruling covers. A note the note checker corrected, or one this session changed under a ruling: record the ruling (The rulings, step 5). Any other change: the human approves again (the interview, step 8). |
| `REFUSED:` naming this session's folder | 3 | Stop. The desktop app refuses this session's writes into the feature tree. Tell the human to start the command from a session whose folder is the main checkout. |
| Any other `REFUSED:` | 3 | Stop and show the human the line. |

The name is lower-case letters, digits and hyphens. The session's folder is the product repo's main checkout, whose `CLAUDE.md` reads `Lane: careful`. The feature lives in its own worktree, `<repo>/.claude/worktrees/feature-<name>`, on the branch `feature/<name>`: when the worktree exists, run the check there; when only the branch exists, add the worktree first (`git worktree add .claude/worktrees/feature-<name> feature/<name>`); when neither exists, run the check in the repo, where it finds no plan, or a merged report on main.

Everything on the page and in the notes is written for the build agents, after reading the code: `templates/change-note.md`, `templates/plan.md` and `templates/report.md` in the skills repo are the three shapes, and the hooks, the note check and the plan check read them line by line. Terms: CONTEXT.md in the skills repo (change note, feature plan, done check, cut, red check, hostile walk, ruling, re-arm, waiting, panel, road finder, reader seat, the count, tooling stop, fix note, held).

## The interview

The human is at the keyboard. The session stays small: subagents read the code and hand back summaries, and every answer he gives is written to the page at once, so a compaction loses nothing. Ask him only the questions of the four kinds; every other fork is a default, written into the note it belongs to.

1. **The worktree.** From local main (`main` or `master`): `git worktree add .claude/worktrees/feature-<name> -b feature/<name> main`. Every file this interview writes goes there, and the run starts there. Done when `git -C <worktree> branch --show-current` prints `feature/<name>`.
2. **The feature.** One question, before any reading: what the feature does, in a few sentences, if the command did not say. Write it as the plan's first paragraph, `changes/<name>/plan.md` from `templates/plan.md`, title and `Feature:` line filled. Done when the paragraph is on the page.
3. **The code.** Read `BRIEF.md` and `docs/design.md` yourself. For each screen, module or table the feature touches, one Explore subagent with a narrow brief returns at most fifteen lines: the files, the pattern they use, the tests beside them, the migration that owns the table. Keep the summaries, never the files. Done when every screen and table the feature names has a summary.
4. **The notes.** Cut the feature into change notes, `changes/<name>/<nn>-<slug>.md` from `templates/change-note.md`, numbered from `01`. Each note is one fresh Sonnet implementer's session: half a page, real button, label and file names from the summaries. A note that adds a shared pattern goes first, and every note that uses it names it on its `Waits for:` line. A migration only adds. `Risk:` names each of money, authentication, secrets, migration and row writes the note touches; a right, a role or a row policy is authentication. `Screens:` names the table's screens, `all <group>`, or `none`, and a note that names a screen carries one end-to-end done check, a Playwright spec, per screen. Each note lists every page that draws a component it changes: search the code for each import of the component, and name the screen of every page that uses it. One feature stopped three final checks on a page that drew a changed card and that no note named. A note that adds a screen adds its row to the screens table of `docs/design.md` in the same commit and carries a `Core design:` line, since the note check reads the table from the index and guards that file. Every done check is one command and what its pass proves. Done when `plan_check.py notes <name> --static` prints `ok` for every note except the test files, which step 5 writes.
5. **The tests.** For each done check, write its test file and name it in the note's `## Tests` part: a Playwright spec against a screen that does not exist yet, from the button and label names in the note and the core design; a vitest file for logic. Each rule a note adds has a test that fails when the rule is removed: a check, a guard, a policy, a limit, a refusal. Four of eight sampled reject reports named a rule with no such test. A test that protects behaviour the note does not change starts its title with `keeps:`. Commit each note with its tests, `note <nn>: <title>`; the hooks fire, and notes and tests are not guarded paths. Take no baseline. Done when every note is committed and `plan_check.py notes <name> --static` prints `ok` for every note.
6. **The pre-run check.** `plan_check.py notes <name>`, which runs every done check on today's code. The Playwright checks need one build of the app, a few minutes, spent now rather than after the human leaves. Fix each `REFUSED` line in the note or its test and commit, then run it again. When it prints `PRUNING:`, the suite is over budget: add the `[pruning]` question to the page. Done when the check exits 0.
7. **The page.** Fill the plan: the notes table, the order in rounds of three at most, and the questions, one line each, of the four kinds and the pruning question when step 6 asked for it. Core design: each pattern a note adds or each screens rewrite, with the check behind it. Migration: each one, and that it only adds. Money or access rules: each price, right, row policy, role or secret a note changes. Data leaving: each route, webhook, push or email format a note commits. Show the human the page, then put the questions one at a time, and write `Answer:` under each the moment he gives it. Done when `plan_check.py plan <name>` names no unanswered question.
8. **The approval.** When the human writes `approve`, append `Approved: <today>` to the page and commit the page and the notes together, `plan: <name> approved`. Run `plan_check.py plan <name>`; it must print `plan: approved`. Then tell him, in two lines: `/clear`, and type `/build-feature <name>` again. End the session there; the clean session sees the approved plan and runs. Done when the check printed `plan: approved` and the two lines are on screen.

## The rulings

The plan check printed `RULING:`. The report on the feature branch shows a note `failed` (three strikes) or stopped on a question. There is no interview, no typed `approve` and no `/clear`: the session rules on each such note and starts the run again in this session. A ruling is the human's answer, the agent's written default, or for a question in a risk class the road a panel's count gives. The session never writes an answer of its own, and it never loosens a gate.

1. **The stop.** Each stop has four typed parts: the note, the class, the question and the default. They are in the run's result under `stops`, and in the report's `## Decide` part as `<nn>: [<class>] <question> Default: <default>`. The class is the one the agent typed, never one the session picks: `feature_run.py roles` (The run, step 5) writes each typed stop to `.git/build-feature/<name>/stops.jsonl` from the agents' transcripts, `record` reads the class there and refuses a `--kind` that differs, and a stop with no class on record is `unclassified`, which waits for the human. A question of the final check has the number `final` and its own report row `final`; no final check runs while that row stops or waits. A `failed` note carries no typed stop: its question is "note `<nn>` failed three strikes", its default is the change its last reject report asks for (the row's `Last report`), and its kind is `re-arm`. A note gets one re-arm, and any other ruling on a failed note is the human's.
2. **Who rules.** For each stop, `python3 ~/.claude/skills/workflow/lib/rulings.py wait <name> --tree <worktree> --note <nn>`, then send the line it prints after `notice:` with `PushNotification`: the question, its default, and for a risk class the form his answer must have. The command records the time the question went out and prints the road:
   - `sent at <time>. His answer rules until <time>; after that the default rules`: the class is `none`. One `ScheduleWakeup` to the latest time printed covers every stop of the run. `record --who default` is refused before that time. A `failed` row needs no `wait`: its re-arm goes by `default` at once.
   - `sent at <time>. His answer rules until <time>; after that the panel rules`: the class is money, access, a migration's direction or data leaving the product. The same wake covers it. After that time run `python3 ~/.claude/skills/workflow/lib/rulings.py panel <name> --tree <worktree> --note <nn>` once per step; it refuses before the time, writes each agent's brief under `.git/build-feature/<name>/panel/` and prints the spawn.
     1. **The road finder.** One `workflow:build-feature-road-finder` agent through the Agent tool, with the description and the one-line prompt the command prints. It looks for a road the question does not offer and that beats every offered road, and writes two at most, or none.
     2. **The three readers.** Three `workflow:panel-review-persona` agents in one message, so they run at the same time, each with the model override `opus` and the description and prompt printed for its seat. The seats are fixed in `lib/rulings.py`: the exposed party, the operator at release and rollback, the next builder. Each judges every road, offered and found, and writes its own file: line 1 is `Rule: <road id>` or `Hold: <the one fact to measure first>`, then its reason, then two conditions at most. The brief the command writes gives the whole form of that file, and says that it replaces the report form of the agent file. Run the command again only when all three have returned. Never show one reader another reader's answer.
     3. **The count.** The command counts the three files; no agent judges, and the session does not. Two or three readers on one road: that road rules, a found road like any other. Take it through steps 3 to 6 with `--who panel` and the road as `--words`, as the command prints. A vote for a road that needs a fact only the human can get is a `Hold` on that fact. No two on one road and fewer than two `Hold`: the written default rules, by `panel`, when one reader chose it, and the entry says the readers disagreed. Every other count rules nothing: the command sets the row to `waiting:`, and the question goes under "Decide" in `~/.claude/pending.md` with the facts to measure. A call while one or two readers have not written is no fault: the command prints "readers still run" and changes nothing, so call it again when all three have returned. A panel that is not sound runs once more: a reader's file with no vote on line 1, an agent with no transcript under its label or not on `opus`, or a reader whose transcript names another reader's answer file. The command removes the three answers, says why and prints the spawns again; spawn every agent it prints. After a second fault it sets the row to `waiting:`. An answer of his that comes before the record still rules, in his name.
   - `waiting: <class>: <question>`: the stop has no class on record, the readers held, or two questions of the note took a ruling without him already; or the stop carries no written default, and then `wait` itself prints this row, for a class of `none` too: a default nobody wrote settles nothing. Nobody answers it for him. Commit as the command prints, and write the question under "Decide" in `~/.claude/pending.md` in the full form of step 1 of The gate. The note waits for him with no timeout, the notes that wait for it wait, and the rest run.
   - His answer is a message he types in this session, at the keyboard or from the phone, after `wait` put the note in front of him. It goes to `record` as `--who <the first word of git config user.name>` with `--words` copied from it: the whole message, or one whole sentence of it. `record` and `answer` read the messages a person typed in this session's transcript and refuse any other words. One sentence answers one question, and a risk-class question takes only a sentence that starts with the note's number and a colon, as in `02: A` or `02: yes, up to 50`; the notice shows him that form. Before his ruling on a `failed` row, a `waiting:` row, a cut or a merged note, run `wait --note <nn>` with no `--why`: it changes no row and records when he saw it. A session with no transcript records nothing in his name.
3. **The change.** Edit the note and its tests inside the words of the ruling, and nothing past them. Under a panel's ruling, write each condition the count printed into the note's `## Done` part, word for word, with its test: the readers who chose the road named those tests, and the plan check refuses the restart without them. One commit applies a ruling (step 6), and the ruling covers that commit alone: a later edit of the same note or test is refused until a new ruling names it, and a test file two notes name is covered only when each has its entry. A cut is the human's ruling alone, and `record` refuses any other who for it: move the note to `changes/<name>/cut/` and delete the test files its `## Tests` part names in one commit, add its line under `## Cut` on the page as `<nn> <title>, cut <date>: <his words>`, set its report row to `cut <date>`, and revert its merge when it had merged (`git revert -m 1 <its merge commit>` on the feature branch). The row stays `cut`.
4. **The reader.** One fresh `workflow:build-feature-ruling-reader` agent per ruling, through the Agent tool, with the feature worktree, the feature name, the note's number, the question, the words of the ruling and the note's diff. It answers per other note `no change` or the exact edit, and ends on a `Touches:` line. For each note it names: when its row is not `merged`, apply the edit and add the number of the note the ruling is on to its `Waits for:` line; when its row is `merged`, never edit it, and write a fix note in its place, `changes/<name>/<next number>-<slug>.md` with its tests, that waits for the note the ruling is on. Each merged note it names takes a fix note of its own.
5. **The record.** `python3 ~/.claude/skills/workflow/lib/rulings.py record <name> --tree <worktree> --note <nn> --kind <the typed class, or re-arm> --who <who> --question "<the question; for a stopped row, the row's own words>" --words "<his words, the default, or the panel's road>" --touches <the reader's line> --undo "<what reversing it costs>"`. `<who>` is `default`, `panel`, or the human's name as step 2 gives it. The command writes the entry under `## Rulings` on the plan page and sets the note's report row to `not started` with no strike. It refuses a row that did not stop, a `--question` that is not the question the row stopped on, a `merged` row or a `waiting:` row for anyone but the human, and a third ruling without him on one note: a note takes two rulings by `default` or `panel` and one re-arm, and its next question waits for him. `--who panel` is taken only for a risk class, only with the panel's files for that stop, only for the road the count gives, and only from the session whose transcripts hold the finder and the three readers under the labels of this question, all four on `opus`. It writes the count and the conditions into the entry. His ruling on a merged note, a sentence that starts with `<nn>:`, records in his name with `--kind none` or its risk class and `--touches` naming its new fix note, which waits for `<nn>`; the row stays `merged`, and the note itself is never edited. Then one entry per touched note and per fix note, with `--kind "follows <nn>"`, the who of the ruling it follows, `--touches none`. In his name it carries the words of the ruling it follows, and `record` refuses any others. Every such entry needs his answer at the gate, whoever made the ruling it follows: it changes a note no question was about. A note the note checker corrected stays in the report's Decide part as `<nn>: [correction] <the checker's line>`: record it with `--kind correction --who default` and that line as the words. The run does not start again before it is recorded, and it holds the merge until he confirms it.
6. **The check and the restart.** `plan_check.py notes <name> --tree <worktree> --only <each changed or new note>` until every one prints `ok`. Commit the plan, the notes, the tests and the report together as `ruling: note <nn>`, one commit per ruling, with the line the last `record` of the ruling printed: it names the feature's folder and each test of the note and of the notes that follow it. `plan_check.py plan <name> --tree <worktree>` must print `plan: approved`; a `REFUSED:` line names what the ruling lacks. Then The run, from step 1, in this session.
7. **A note that waits.** A `waiting:` row has no timeout and holds only the notes that wait for it. The script writes one itself when a note fails three strikes after its re-arm, and for the row `final` when the final check has no fix round left. Its line stays under `## Decide` across every restart. When the human is at the keyboard, show him each waiting row in two lines, with its last reject report or its question, run `wait --note <nn>` so the time he saw it is on record, and take his answer through steps 3 to 6 with his name as who.

## The gate

The plan check printed `GATE:`. The run's final check passed, the report reads `State: held`, and the feature is not in local main: one or more rulings were not made by the human, and he confirms each once, here. A ruling he made himself needs no confirmation; a `[follows <nn>]` entry does, unless he cut its note since. Three git hooks hold the main branch while a line has no answer: `pre-merge-commit` on a merge commit, `reference-transaction` on a fast-forward, a reset, a commit and a plain `git update-ref`, and `pre-push` on a push of it. `when-a-run-stops.md` states what they do not stop.

1. **The list.** `python3 ~/.claude/skills/workflow/lib/rulings.py list <name> --tree <worktree>`; the report carries the same lines under `## Ruled while you were away`. The command records the time, and `answer` refuses before it ran: an answer is a message he types after he saw the list. Show a line outside the risk classes as it is: the question, the road taken, who took it, the notes it touched and the undo cost. A risk-class line opens with its class in bold capitals and takes the full form: what it is in plain words, one worked example from the feature, what follows from yes and from no, the case for each at its best, what was checked or "nobody measured this", what it costs to change later, what a wrong answer costs, and the recommendation with the fact that would flip it. A panel's line brings its own facts, and the command prints them: the count, each reader's vote and reason, the conditions, each found road as "a road the question did not offer" with its evidence and undo cost, and each candidate road with the fact it needs from him.
2. **The answers.** One sentence from him, such as "confirm all", covers the lines outside the risk classes: `rulings.py answer <name> --tree <worktree> --all --words "<that sentence>"`. Each risk-class line takes a sentence of his that starts with its number and a colon, as in `03: confirm` or `03: yes, no price`; the list command prints that form, so show it to him with the list: `rulings.py answer <name> --tree <worktree> --note <nn> --confirmed --words "<that sentence>"`. `--words` is a whole message or one whole sentence he typed after the list; the command refuses any other, and a sentence that answered one line answers no second one.
3. **An overturned line** becomes a fix note that the run builds, never an edit of an old note. Write the note that undoes the ruling as he says, `changes/<name>/<next number>-<slug>.md` with its tests, and record its entry (The rulings, step 5) with `--kind "follows <nn>"` and the who of the line it follows. Then `rulings.py answer <name> --tree <worktree> --note <nn> --overturned --words "<his words>" --fix <the fix note's number>`; the command refuses a `--fix` note that is merged or cut. He confirms the fix note's own line at the next gate, after the run built it.
4. **The restart.** Commit as `rulings: answered`, and run `plan_check.py plan <name> --tree <worktree>` until it prints `plan: approved`. Then The run. With every line confirmed and no code changed since the final check, the run goes straight to the merge; a run that builds any note runs the final check again before the merge.

## The run

The plan check printed `plan: approved`. The session starts the `build-feature-run` workflow and watches it; the seven roles in `~/.claude/skills/workflow/agents/build-feature-<role>.md` do the work, and `changes/<name>/report.md` on the feature branch is the ledger the merger keeps. Nobody answers a question mid-run: a note that needs an answer stops with its class, its question and its default in the role's typed answer, the other notes run on, and the session rules after the run ends (The rulings).

1. **The pre-run check.** `plan_check.py notes <name> --tree <worktree> --only <every note whose report row is not started>`. A note whose done check now passes stops: write its row as `stopped: done check passes before the work` in `changes/<name>/report.md` on the feature branch (from `templates/report.md` when the file does not exist yet), with its line under `## Decide`, `<nn>: [none] the done check passes before the work: is it built already?`, and commit it as `report: note <nn> stopped`. No agent wrote a default for this stop and the session writes none, so `rulings.py wait` sets its row to `waiting:` and the human answers it (The rulings, step 2). The notes that wait for it wait, and the rest run. A note whose branch a merge commit brought into the feature never stops here: the check prints `merged into feature/<name> at <commit>` for it and runs none of its done checks, whatever its row says. Done when the check exits 0 or every refused note has its row.
2. **The arguments.** `python3 ~/.claude/skills/workflow/lib/feature_run.py args <name> --tree <worktree>`, with `--role <role>=<model>:<effort>` for each override in the command (`implementer=opus:medium`). It prints the JSON the workflow takes: the note graph from the `Waits for:` lines, each note's state from the report, or `merged <commit>` when git holds the merge of its branch and a run ended before the row was written, the lines an earlier run left in the report, the paths, the models and efforts, and `started` from the clock; never type a time by hand; and from the plan's rulings the wait, the lines that still need his answer, the row `final` when it stops or waits, and whether an earlier final check stands. A note is `fresh` when its row says so, and always when its file or its tests changed after its note branch's base commit: the old tree holds the build of the old note. The command refuses to print the arguments while such a note's old worktree or branch exists, and its `REFUSED:` line prints the commands that remove them: `git -C <repo> worktree remove --force <worktree>`, `git -C <repo> branch -D <branch>`, `git -C <repo> worktree prune`. Run them from this session, then the command again. No agent can: the auto-mode classifier refuses `git worktree remove --force` as irreversible. A note whose merge into the feature did not go through stops as `stopped: worktree:` and takes the same removal. A `REFUSED:` line also stops here when the rulings on the plan page do not hold, a correction has no entry yet (The rulings, step 5), the product's `reference-transaction` hook is missing, not executable or not on `core.hooksPath`, or the run started three times in a row by itself with no newly merged note. For that last one there is no further restart: each row the line names waits for the human, `rulings.py wait <name> --tree <worktree> --note <nn> --why "tooling: <its line>"`, and the other notes run on. A final check that no run finishes is counted the same way, and waits as `--note final`. Done when the JSON is on screen.
3. **The start.** `mcp__ccd_host__request_keep_awake` with `until: session_idle`, then the `Workflow` tool with `scriptPath` `~/.claude/skills/workflow/workflows/build-feature-run.js` and `args` set to that JSON as an object, never as a string. Keep the task id and the transcript dir the result gives. The script runs each note in its own worktree, `<repo>/.claude/worktrees/note-<name>-<nn>` on `note/<name>/<nn>`, three notes at once, a verifier and a reviewer per attempt, the note checker at strike two, three strikes to fail, one merger at a time, and three fix rounds for the final check; every reject report goes under `.git/build-feature/<name>/`, never under `changes/`. Done when the result says the run started.
4. **The watchdog.** `ScheduleWakeup` for 1,800 seconds, prompt `watch build-feature <name>`. On each wake: when the task has finished, go to step 5. Else read the newest change time among `<worktree>/changes/<name>/report.md`, every file under the transcript dir, and every `agent-*.jsonl` in the session's `subagents/` folder two levels above it: an agent's own subagents write there, and the final reviewer's `/code-review` writes nowhere else for 20 to 30 minutes. Moved within the last 30 minutes: schedule the next wake. Nothing moved: `TaskStop` the task, take the last line of the newest `agent-*.jsonl` as the error, send `PushNotification` `<name>: nothing moved for 30 min: <error>`, and start again from step 1; a new run reads the report and skips the merged notes. The bound on restarts is in code, not in the session's count: step 2 refuses the fourth start in a row with no newly merged note, and any start after three days with none. A start whose only such rows are an outage (`stopped: API errors`, `stopped: <role> returned no result`) does not count toward the three; only the three days end it. On that refusal, notify and end the session.
5. **The end.** The result carries `state` (`merged`, `held` or `stopped`), `notes`, `stops`, `fix_notes`, `halted` and `notice`. Send `notice` with `PushNotification`. First of all, `python3 ~/.claude/skills/workflow/lib/feature_run.py roles <transcript dir> --report <report path>`, on the feature worktree, or on local main when the feature merged: it fills the tokens and cost cells, and writes each typed stop to `.git/build-feature/<name>/stops.jsonl`, which every ruling reads. Commit the report as `report: <name> roles`. Then, by what the result holds:
   - `halted` names a role that returned no result twice, a usage limit the runtime stopped waiting for or an outage: wait for the reset when the task panel named one; when none is named (an outage), `ScheduleWakeup` for 1,800 seconds and start again on the wake; then start again from step 1 as one of the three.
   - A stop of kind `tooling` (a row `stopped: tooling: <tool>: <its line>`) is a fault of the tools, never a question. Apply the repair `when-a-run-stops.md` lists for it in a row whose owner is the session, and start again from step 1 with no question. A repair that changes the note is a ruling by `default` and needs no wait: a screen the commit hook names goes on the note's `Screens:` line, recorded with `--kind screen`, and the human confirms it at the gate. When no listed repair applies, the note waits: `rulings.py wait <name> --tree <worktree> --note <nn> --why "tooling: <its line>"`, and one item under "Decide" in `~/.claude/pending.md` with the refusal line and the path of the evidence. A gate is never loosened without the human: no skipped hook, no weaker check, no second tool to do what the first refused.
   - A stop of kind `question`, or a `failed` row: The rulings, in this session.
   - `fix_notes` holds a final-check finding that needs a new test, and the row `final` reads `stopped: fix note needed: <the findings>`, a question of class `none`. Take it through The rulings with `--note final`: after the wait, record it by `default`, write a fix note for each finding, `changes/<name>/<next number>-<slug>.md` with the test, and record each with `--kind "follows final"`. The human confirms those lines at the gate. A question a fix round asked goes the same road with its own typed class, a panel included.
   - `held`: the final check passed and the merge waits for the human's answers. End the session. The next `/build-feature <name>` opens The gate.
   - A final check that still finds faults after its three fix rounds writes the row `final` as `waiting:`. The three are per feature: a restart counts the rounds the report holds, and neither a restart nor his answer gives a new one. Write it under "Decide" in `~/.claude/pending.md` with the findings. His answer goes through The rulings with `--note final`, as a fix note; a finding on main is fixed on main first. The next run then brings main in and runs the final check and the merge again.

   Done when the notice was sent, the roles cells are filled and every stop has its ruling, its repair or its `waiting:` row.

The runtime itself waits for a usage-limit reset twice and restarts an agent whose output stops up to five times; the script requeues a note whose agent returned no result once, then stops the run; a final role with no result twice ends the run with no fix round spent, and the next start runs the final check again. The allow rules the build agents need are in the global settings, `permissions.allow`; the list is `build-feature/allow-rules.md`, and the first long run is the place to add what still prompts.

A one-note change never uses this skill. It runs as one `/goal` session, and that session runs `plan_check.py notes changes/<nn>-*.md` once before it builds; a refusal stops it.
