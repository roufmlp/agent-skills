# When a run stops

What a stopped `/build-feature` run looks like, what it means and who does what next. Every row is a case that happened: the greeting run on the rehearsal clone (2026-11-03, one note, three runs), the stamps rehearsal (2026-11-04, three notes, four runs) or the first product features (2026-11-08 to 2026-11-11). The version 2 README's "When something stops" part starts from this table.

A row whose last cell reads "The session" is a repair the session applies with no question, then it starts the run again. A row that names the human waits for him, with no timeout, and the other notes run on. No row loosens a gate: a hook or a check that refuses is repaired as its row says, or it waits.

Where to look first: `changes/<name>/report.md` on the feature branch (`State:`, the notes table, `## Final check`), then the report the row names under `.git/build-feature/<name>/`, then the Workflow task panel.

The run did not merge and the final check did not run. | The re-arm, once per note: the default is the change the last reject report asks for. The session edits the note inside it, writes the `Ruled:` line by `default` on the plan page, sets the row to `not started` and starts again in the same session, with three new strikes. `rulings.py record` takes `--kind re-arm` from `default` for a failed row and refuses any other kind from it: every other ruling on a failed note is the human's. | The session |

The notes that do not wait for it ran on. | Type `/build-feature <name>`. The session shows the last reject report; he changes the note or cuts it. A cut deletes the note's tests too, and reverts its merge if it had one. | the human, at the keyboard |
| A note row reads `stopped: done check passes before the work`, or `stopped:` with an implementer's or the note checker's reason, and `## Decide` in the report carries its line | The note needs an answer. No agent is the judge. | A note row reads `waiting: money:`, `waiting: access:`, `waiting: migration:` or `waiting: data leaving:` with a question | A panel did not rule the question. It is under Decide in `~/.claude/pending.md` in the full form, with the facts the readers named. | Answer it, then `/build-feature <name>`: the session takes his words as the ruling and starts again. | the human |
| `rulings.py panel` prints "is not sound", or `panel` or `record --who panel` prints `REFUSED:` | The line names what the panel lacks. Not sound: a reader's file whose line 1 is not `Rule: <a listed road>` or `Hold: <fact>`; a reader's file that is missing while another is there; an agent with no transcript in this session under the label of this question; an agent on another model than `opus`, the finder included; a reader whose transcript names another reader's answer file. Refused: the wait is not over; the finder's file is not in its typed form (at most two found roads, each with `file:line` evidence); `--words` is not the road the count gives; `--question` is not the question the row stopped on. | Not sound: `panel` has removed the three answers, and the finder's when the fault is the finder's, and printed the spawns again. Spawn every agent it printed, the three readers in one message. It does this once: after a second fault it sets the row to `waiting:`, the row above. Refused: do what the line names. Never write a reader's file from the session, and never record another road. | The session |
| A note row reads `waiting: unclassified:` | An agent stopped with no typed class, or with one the script does not know, or the stop is not in the run's record (`feature_run.py roles` did not run before the ruling). No default and no panel rules it: nobody knows which seats its question needs until somebody reads it. | Answer it, and name its class, then `/build-feature <name>`. | the human |

Five stops, 2026-11-08 to 2026-11-11, were this one guard; from sessions whose folder is the main checkout, 73 agent writes passed and none was refused. | Since 2026-11-12 the plan check refuses such a session at the start, so this row should not show. The red check and the note check are gates: a refusal from them is never worked around. | `rulings.py wait` sets the row to `waiting: tooling: <its line>`; one item under Decide in `~/.claude/pending.md` carries the refusal line and the path of the evidence. The other notes run on. A repair found this way gets its row here. | the human |
| A note row reads `stopped: worktree:` | The note starts again in a new tree: its merge into the feature did not go through, or the merger could not make its tree. The old tree holds the old build, and an agent may not remove one: the auto-mode classifier refuses `git worktree remove --force`. | Start again. `feature_run.py args` refuses the start while the old tree is there and prints the commands that remove it; the next row. | The session |
| `feature_run.py args` prints `REFUSED:` and "needs a new tree" | A note starts again and its old worktree or branch still exists: a ruling changed the note or its tests after the branch was cut, a run was killed while the row read `running`, or the row reads `stopped: worktree:`. Nothing else keeps a run off the old build, so the command refuses to print the arguments. | Run the commands the line prints, from the session: `git worktree remove --force`, `git branch -D`, `git worktree prune`. Then `args` again. | The session |
| A note row reads `stopped: API errors` or `stopped: <role> returned no result`; `halted` names the role | An agent returned nothing twice: a usage limit the runtime stopped waiting for, or an outage. | Wait for the reset the task panel names, then start again; an outage names none, so wait 30 minutes, then start again. The report skips the merged notes. `feature_run.py args` counts the starts in `.git/build-feature/<name>/starts.json` and refuses the fourth in a row with no newly merged note (`MAX_STARTS_WITHOUT_MERGE`); a start whose only such rows are these two does not count, so an outage ends only at the three-day limit (`MAX_OUTAGE_SECONDS`; the human, 2026-11-04). | The session |
| The row `final` reads `waiting: the final check found faults and has no fix round left`, or `found faults after main moved` | The three fix rounds did not clear the final check. The three are per feature (`FIX_ROUNDS`): a restart counts the `Fix round` lines under `## Final check`, and neither a restart nor his answer gives a new round. A final check that runs again because main moved gets none either. Each round takes every finding of both final roles in one batch. Twice on the clone a fix round itself added a rule no note names (a budget test, a tables guard), and the final reviewer refused it; since 2026-11-04 the pre-commit hook refuses such a test file on the feature branch. | He reads the findings under `## Final check` and says what to do. A final check that still fails waits for him again. | the human |
| The row `final` reads `stopped: fix note needed:`, or `stopped:` with a question a fix round asked | A finding needs a new test, and a fix round may not add one: the hook refuses a test file no note names. Or the fix-round implementer asked a question. No final check runs while the row stops or waits. | The rulings, with `--note final`: the question goes out, the default rules a class `none` after the wait, and each fix note is recorded with `--kind "follows final"`. A question in a risk class takes a panel (`rulings.py panel --note final`). He confirms every such line at the gate. | The session; the human at the gate |
| `State: held`, and the plan check prints `GATE:` | The final check passed, and one or more lines wait for him: a ruling by `default` or `panel`, a correction by the note checker, and every touched note and fix note (an entry `[follows <nn>]`), whoever made the ruling it follows, unless he cut that note since. A panel's line carries the count, each reader's vote and reason, the conditions, each road the finder found and each candidate road with the fact it needs from him. The feature stays off local main until he answers each. Three hooks hold the main branch: `pre-merge-commit` on a merge commit, `reference-transaction` on a fast-forward, a reset, a commit and a plain `git update-ref`, and `pre-push` on a push of it. | Type `/build-feature <name>`. One sentence such as "confirm all" answers the lines outside the risk classes; each risk-class line takes a sentence that starts with its number and a colon, as in `03: confirm`. An overturned line becomes a fix note the run builds. | the human |

A merged note's done-check edit no longer counts (fixed 2026-11-04). | A change the session made under a ruling: record the ruling (`rulings.py record`) and commit the change and the entry in one commit. | `REFUSED:` says a merged note is never edited | A ruling changed the text of a note that had merged, or `rulings.py record` named a `merged` row. The tests of a merged note are not watched: its implementer and the fix rounds edit them, and the reviewers and the final check read those edits. | Restore the note (`git checkout <its merge commit> -- <the note>`) and write a fix note in its place, with its own entry `[follows <nn>]`. Each merged note a ruling touches takes a fix note of its own. | The session |
| `REFUSED:` says a note "corrected by the note checker" has no entry | The note checker corrected the note at strike two, and the report's Decide part carries `<nn>: [correction] <its line>`. The line holds the merge until he confirms it. | The session; the human at the gate |
| `rulings.py record` or `answer` prints `REFUSED:` about his words: no message he typed is the words, a sentence answered already, the words do not start with the line's number, or the note or the list was not shown yet | A ruling or an answer in the human's name quotes him. What the app adds to a message (a `<system-reminder>` block, the text of a slash command) is not his words. `--words` is the whole message or one whole sentence of it. One sentence answers one line, apart from "confirm all". A risk-class line takes only a sentence that starts with its number and a colon, as in `02: A` or `03: confirm`. He sees that form where he is asked: `wait` prints it in the notice, and `list` prints it under the gate list. | Run `wait` or `list` first, and copy `--words` from the message he types after it, exactly. **What the guards do not stop.** They stop a session that takes the easy road: one that writes an answer itself, or merges without the gate. They do not stop a session that works round them on purpose, and no case is added for that. Outside them are a forged answer (a transcript the session writes itself, another session's id in `CLAUDE_CODE_SESSION_ID`, a `Ruled:` or `Confirmed:` line typed into the plan by hand), a forged panel (a reader's file the session writes itself after an agent with the reader's label ran: `record` checks that the agents ran and on which model, not that each wrote its own file), a reader that opens another reader's answer by a path its transcript does not spell out (`record` looks in each reader's transcript for the path of the other two answer files, and a glob or a `cd` first shows none), git run with the hooks off (`-c core.hooksPath=`, or `--no-verify` on a push), and six roads of git plumbing that move the main branch past the `reference-transaction` hook: `git update-ref -d` on it and then `git update-ref`; `git branch -M main` on the feature branch; `git branch -D main` and then `git branch main <feature>`; `git symbolic-ref refs/heads/main <feature>`; `git push --no-verify . <feature>:main`; and `git update-ref` from a linked worktree whose checkout has no `.githooks` folder. The agents' git guard refuses the hooks-off forms and passes the first four roads. The backstop is the push, which is the human's: `pre-push` reads the plan pages again. The guards also stop one move that is no fault: a pull of a merged feature on a clone whose `user.name` is another person's. The plan page names the person of the machine that merged it, the gate reads every page the same way, and so the hook refuses the pull with "is not `default`, `panel` or `<the clone's name>`". On such a checkout, which merges no feature, a person pulls with `git -c core.hooksPath=/dev/null pull`. An agent does not: the git guard refuses that form.

Costs seen on the clone, for the budget: a one-note feature, three runs, $14.45; a three-note feature with one cut, four runs, 50 agents, $19.52 and about three hours, of which the final check was $13.74. The final check runs the clone's whole suite (400 to 540 s), every end-to-end spec (675 s) and the gate, so each pass is 30 to 75 minutes; the levers are a green main and the pruning answer, not the workflow.
