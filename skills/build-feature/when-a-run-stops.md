# When a run stops

What a stopped `/build-feature` run looks like, what it means and who does what next. Every row is a case that happened: the greeting run on the rehearsal clone (2026-11-03, one note, three runs), the stamps rehearsal (2026-11-04, three notes, four runs) or the first product features (2026-11-08 to 2026-11-11). The version 2 README's "When something stops" part starts from this table.

A row whose last cell reads "The session" is a repair the session applies with no question, then it starts the run again. A row that names the human waits for him, with no timeout, and the other notes run on. No row loosens a gate: a hook or a check that refuses is repaired as its row says, or it waits.

Where to look first: `changes/<name>/report.md` on the feature branch (`State:`, the notes table, `## Final check`), then the report the row names under `.git/build-feature/<name>/`, then the Workflow task panel.

| What you see | What it means | What you do | Who |
| --- | --- | --- | --- |
| A note row reads `failed`, 3 strikes, and `Last report` names a reviewer or verifier report | Three attempts were rejected. The run did not merge and the final check did not run. | The re-arm, once per note: the default is the change the last reject report asks for. The session edits the note inside it, writes the `Ruled:` line by `default` on the plan page, sets the row to `not started` and starts again in the same session, with three new strikes. `rulings.py record` takes `--kind re-arm` from `default` for a failed row and refuses any other kind from it: every other ruling on a failed note is the human's. | The session |
| A note row reads `waiting: failed again after its re-arm` | The note failed three strikes twice. Nobody rules on it but the human, and there is no timeout. The notes that do not wait for it ran on. | Type `/build-feature <name>`. The session shows the last reject report; he changes the note or cuts it. A cut deletes the note's tests too, and reverts its merge if it had one. | the human, at the keyboard |
| A note row reads `stopped: done check passes before the work`, or `stopped:` with an implementer's or the note checker's reason, and `## Decide` in the report carries its line | The note needs an answer. The line holds the class, the question and the agent's written default. | `rulings.py wait --note <nn>` records the time the question went out and prints until when his answer rules; the session then sends the question and the default to the phone. `rulings.py record --who default` is refused before that time. The class is the one the agent typed, read from `.git/build-feature/<name>/stops.jsonl`; a `--kind` that differs is refused. A note takes two rulings by `default`; its third question waits for him. The session edits the note, runs the ruling reader, records the `Ruled:` and `Touches:` lines and starts again. | The session; the human inside the wait |
| A note row reads `waiting: money:`, `waiting: access:`, `waiting: migration:` or `waiting: data leaving:` with a question | The question is in a risk class, so no default rules it. It is under Decide in `~/.claude/pending.md` in the full form. | Answer it, then `/build-feature <name>`: the session takes his words as the ruling and starts again. | the human |
| A note row reads `waiting: unclassified:` | An agent stopped with no typed class, or with one the script does not know, or the stop is not in the run's record (`feature_run.py roles` did not run before the ruling). The run treats it as a risk class until somebody reads it. | As the row above. | the human |
| A note row reads `stopped: tooling: desktop app:` and the line says the path "is in the base repo checkout" or "belongs to a different worktree" | The desktop app refuses Write and Edit from a session it placed in its own worktree, for every path in the main checkout (the reject reports under `.git/build-feature/` too) and in any other worktree. Five stops, 2026-11-08 to 2026-11-11, were this one guard; from sessions whose folder is the main checkout, 73 agent writes passed and none was refused. | Since 2026-11-12 the plan check refuses such a session at the start, so this row should not show. If it does: start `/build-feature <name>` from a session whose folder is the main checkout. | the human starts the session; the plan check refuses |
| A note row reads `stopped: tooling: hook:` and the line names the code rules gate | The hook refused an agent's first code edit because the agent had not loaded the code rules. It refused code files only, never a report or a note. | Start again; the implementer's brief loads the skill first. | The session |
| A note row reads `stopped: tooling:` and no row of this table names its line | A hook, a check script or the app refused a step, and no repair is listed; or the script itself threw (`tooling: other: script error:`). The red check and the note check are gates: a refusal from them is never worked around. | `rulings.py wait` sets the row to `waiting: tooling: <its line>`; one item under Decide in `~/.claude/pending.md` carries the refusal line and the path of the evidence. The other notes run on. A repair found this way gets its row here. | the human |
| A note row reads `stopped: worktree:` and the merger's report says the classifier denied `git worktree remove` | A fresh retry needed the old worktree gone, and an agent may not remove one. | Remove it from the session (`git worktree remove --force`, `git branch -D`, `git worktree prune`), then start again. Step 2 of the run does this for every `fresh` note. | The session |
| A note row reads `stopped: API errors` or `stopped: <role> returned no result`; `halted` names the role | An agent returned nothing twice: a usage limit the runtime stopped waiting for, or an outage. | Wait for the reset the task panel names, then start again; an outage names none, so wait 30 minutes, then start again. The report skips the merged notes. `feature_run.py args` counts the starts in `.git/build-feature/<name>/starts.json` and refuses the fourth in a row with no newly merged note (`MAX_STARTS_WITHOUT_MERGE`); a start whose only such rows are these two does not count, so an outage ends only at the three-day limit (`MAX_OUTAGE_SECONDS`; the human, 2026-11-04). | The session |
| The row `final` reads `waiting: the final check found faults and has no fix round left` | The three fix rounds did not clear the final check, and the three are per feature (`FIX_ROUNDS`): no restart gets more until the human answers. Each round takes every finding of both final roles in one batch. Twice on the clone a fix round itself added a rule no note names (a budget test, a tables guard), and the final reviewer refused it; since 2026-11-04 the pre-commit hook refuses such a test file on the feature branch. | He reads the findings under `## Final check` and says what to do; the session records his words with `rulings.py record --note final`, makes the change on the feature branch and starts again: the final check and the merge run again, about 50 minutes on the clone. | the human |
| The row `final` reads `stopped: fix note needed:`, or `stopped:` with a question a fix round asked | A finding needs a new test, and a fix round may not add one: the hook refuses a test file no note names. Or the fix-round implementer asked a question. No final check runs while the row stops or waits. | The rulings, with `--note final`: the question goes out, the default rules a class `none` after the wait, and each fix note is recorded with `--kind "follows final"`. A question in a risk class waits for the human. He confirms every such line at the gate. | The session; the human for a risk class |
| `State: held`, and the plan check prints `GATE:` | The final check passed. One or more rulings are not his: by `default` or `panel`, a correction by the note checker, or a touched note or fix note his own ruling did not name. The feature stays off local main until he answers each. Two hooks refuse every road into `main` or `master`: `pre-merge-commit` on a merge commit, `reference-transaction` on a fast-forward, a reset and `git update-ref`. | Type `/build-feature <name>`: one "confirm all" for the lines outside the risk classes, his own words for each risk-class line. An overturned line becomes a fix note the run builds. | the human |
| `## Final check` holds `On main:` lines | Faults that hold on local main too: red specs, baselines that differ, a table without RLS. Not the feature's, and never a ground. Since 2026-11-04 `lib/on_main.py` writes them: it runs the failed command here and on main and compares the failing tests by name, so no verifier decides. | Nothing for this run. Fix main in its own session when it matters. | the human decides |
| The final reviewer's report says the session answered its own question | An `Answer:` on the plan was written by the session, or a `Ruled:` line carries the human's name with words he did not give. The reviewer refuses the run on it, every time. A `Ruled:` line by `default` or `panel` is no fault: the reviewer reads it against the diff and its `Touches:` line. | the human writes the answer in his words; the session records it, commits and starts again. | the human |
| A row reads `merged` and its `Last report` is a REJECT | The script read the verdict wrong (fixed 2026-11-04: every role answers in a typed form the runtime checks, so a verdict cannot be misread from prose). | Stop the task. On the feature branch `git revert -m 1 <merge commit>`, set the row to `failed`, commit, then start again: the row takes its re-arm. | The session |
| `REFUSED:` names a note, a test or the plan as changed after the approval | A change that no entry under `## Rulings` covers. A merged note's done-check edit no longer counts (fixed 2026-11-04). | A change the session made under a ruling: record the ruling (`rulings.py record`) and commit the change and the entry in one commit. The line says so when the file changed after that commit ("one commit applies a ruling") or when a second note that names the file has no entry. Any other change: the human reads it and approves again, which writes a new `Approved:` line. | The session for a ruling; else the human |
| `REFUSED:` names a `Ruled:` line with no `Touches:` line | The ruling reader did not run, so nobody read the ruling against the other notes. | Run the reader, apply its edits, record the entry again with its `Touches:` line. | The session |
| `REFUSED:` says a merged note is never edited | A ruling changed the text of a note that had merged, or `rulings.py record` named a `merged` row. The tests of a merged note are not watched: its implementer and the fix rounds edit them, and the reviewers and the final check read those edits. | Restore the note (`git checkout <its merge commit> -- <the note>`) and write a fix note in its place, with its own entry `[follows <nn>]`. Each merged note a ruling touches takes a fix note of its own. | The session |
| `REFUSED:` says a note "corrected by the note checker" has no entry | The note checker corrected the note at strike two, and the report's Decide part carries `<nn>: [correction] <its line>`. Nothing the human did not decide reaches local main without his answer. | `rulings.py record --note <nn> --kind correction --who default`, with the checker's line as the words; commit; start again. The line holds the merge until he confirms it. | The session; the human at the gate |
| `rulings.py record` or `answer` says no message he typed contains the words | A ruling or an answer in the human's name must quote him. The command reads the messages a person typed in this session's transcript (`CLAUDE_CODE_SESSION_ID` names the file) after the question went out. | Copy `--words` from his message, exactly. When he did not answer: the default rules a class `none` after the wait, and a risk class waits. Never record in his name without his words. | The session |
| `git merge` into `main` or `master` prints `REFUSED:` and "The branch did not move" | The `reference-transaction` hook refused a road that skips `pre-merge-commit`: a fast-forward, `--no-verify`, a reset or `git update-ref`. After a refused fast-forward the checkout holds the feature's files staged. | `git read-tree -u --reset HEAD` puts the checkout back. Then the gate: the lines wait for the human. | The session; then the human |
| `feature_run.py args` prints `REFUSED:` and "has no `reference-transaction` hook" | The product installed its hooks before the gate, so a fast-forward into its main branch would skip the gate. | On the main branch: copy `reference-transaction` and `prepare` from `~/.claude/skills/workflow/templates/githooks/` into `.githooks/`, run `sh .githooks/prepare`, commit the two files by name, then start again. | The session |
| `feature_run.py args` prints `REFUSED:` and "automatic restarts in a row merged no new note" | The run started three times by itself and merged nothing new. The same tool line can stop every run, and the plan check passes each one. | No further restart. Each row the line names waits for the human: `rulings.py wait --note <nn> --why "tooling: <its line>"`, one item under Decide in `~/.claude/pending.md`. The other notes run on. | the human |
| `REFUSED:` names the session's folder as another worktree of the repo | The session was started in an app worktree, where the desktop app refuses the build agents' writes (the `stopped: tooling: desktop app:` row). | Start the command from a session whose folder is the main checkout. | the human |
| `REFUSED:` names a `Waits for:` that points at a note that is gone | A cut note had dependants. | In the ruling that cuts it, change each dependant's `Waits for:` or cut it too. | the human |
| A verifier REJECT on step 5 shows the same pixel count at the base commit | The committed baselines do not match this machine's render; the note touched no screen. `lib/on_main.py --twice` reruns the screen and runs it at the base, and the verifier passes the step on its `on main:` line. | Nothing for the run. If it keeps rejecting, retake the baselines on main in a session and commit them. | The session |
| The red check refuses "no new test title" | The note's done-check tests were committed at the interview, so the branch adds no new title. | Nothing. The implementer adds a `keeps:` test or a placement test; the report lists it under Defaults taken. | Nobody |
| The red check refuses a fix round that only strengthened a test | A stronger test passes on the pre-fix code, and the red check reads that as weak. | Nothing. The implementer labels it `keeps:`; the final reviewer reads it. A red check that takes a strengthened test is a later change to `suite.py`. | Nobody |
| A reviewer REJECT says a rights test proves nothing because local Postgres grants a new table nothing | A revoke test that reads the table as migrated here cannot go red. The repo's shape grants Supabase's defaults back in a rolled-back transaction and runs the rights block again. | Nothing at strike one. At strike two the note checker corrects the test inside what the human approved, and the session records the correction as a ruling by `default` at the next start. | The note checker |
| The final verifier's report says the full suite is over budget | A line under `## Time`, not a finding, by the human's ruling of 2026-11-03 for the clone. | For Orderflow: the first interview asks the pruning question; the human answers it once. | the human |
| Nothing moved for 30 minutes: the report and the transcripts have the same change time | An agent hung, or the runtime is waiting on something it does not say. | The watchdog stops the task, sends the last transcript line to the phone and starts again. | The session |
| The Workflow tool refuses `scriptPath` | The script must be a file the session may already read. `Read(~/.claude/skills/**)` is in the human's settings since 2026-11-04, so this should not show. | If it still shows: `mcp__ccd_directory__request_directory` on `~/.claude/skills/workflow/skills/build-feature`, then start again; if that fails too, start from the skills repo and tell the human the rule did not hold. | The session |
| The report on main says `State: running`, or lacks the final check | The merge carried an old report (fixed 2026-11-04: the final report is written before the merge). | Copy the feature branch's report onto main and commit it as `report: <name> merged`. | The session |
| After the run, `git status` in the feature worktree shows retaken baselines or `changes/<name>/screens.md` uncommitted | The merger's baselines job did not run (fixed 2026-11-04: it runs after every final verifier). | Commit them as `baselines: <screens>` and start again. Removing the worktree loses them. | The session |
| The e2e global setup fails on a migration the branch does not have | The tree's claimed database still holds a cut note's migration. | Drop the batch's databases (`node scripts/run-db.mjs drop --batch <id>`) before the restart; a fresh claim rebuilds from empty. | The session |
| The final check fails on a test of a cut note | The revert of the note's merge restored the test the interview committed with it. | Delete the note's test files in the cut (the cut does this since 2026-11-04), commit, start again. | The session, under the human's cut |
| No notice on the phone though the result said "Mobile push requested" | The push left the app; the phone side is Remote Control's. | Check the app's notifications. Nothing to fix in the run. | the human |

Costs seen on the clone, for the budget: a one-note feature, three runs, $14.45; a three-note feature with one cut, four runs, 50 agents, $19.52 and about three hours, of which the final check was $13.74. The final check runs the clone's whole suite (400 to 540 s), every end-to-end spec (675 s) and the gate, so each pass is 30 to 75 minutes; the levers are a green main and the pruning answer, not the workflow.
